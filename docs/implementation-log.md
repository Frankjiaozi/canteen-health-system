# 实施记录

这份文档回答一个问题：**当前这个系统为什么长成现在这样**。

[docs/architecture.md](./architecture.md) 描述的是「现在的状态」——目录怎么分、数据怎么流；
这里记的是过程：每一步做了什么、踩到了什么坑、当时为什么这样定。
需求文档记「要什么」，架构文档记「是什么」，这里补上「怎么来的」——
否则这些判断只存在于提交信息里，过两个月谁也翻不出来。

按模块倒序记，最近的在最前面。

## 模块 24 · 一句话录一餐，以及通用只读出口 call_api

### 一句话录一餐

「今天午餐做了米饭 620 份、番茄炒蛋 400 份……就餐 680 人，油 4200 克」——一句话录进采集单。
这是全系统**影响面最大**的一次写入：人次与油盐糖进看板与人均摄入，份数进预测的历史序列，
菜品进公开大屏。所以方案里逐项列出来，并明确说会重算哪些指标；模型的表现也符合预期——
它自己先把三道菜逐个查了一遍确认能对上，再把整份方案摆出来，还主动指出「你没提剩餐量，
所以这次没录剩餐重量和剩余比例」。

**撤回要比别的操作多做一件事**：原来有采集记录的写回原来那条；原来没有的就把这次误录
整份丢掉——而且必须**连人均口径的营养结果一起清**。人均值是按「出餐份数 ÷ 人次」算的，
采集记录没了它就失去依据，留着会让看板继续把它算进去（那是错的数）。单份值不动：
它只依赖配方，正好是「没采集时该有的样子」。

菜单调整（`set_menu_day`）则拒绝已经录过采集的日子：那一天的菜单以实际供应为准，
要改就改采集单，否则会出现「菜单与实际对不上」而营养结果是按菜单算的。

### call_api：给「没包成工具」的查询留一个受控出口

用户问得对：手写工具意味着「没见过的情况就干不了」。系统有 58 个 REST 接口，
助手只有 14 个工具。所以加了通用只读出口，但把三条线画死：

1. **只读**：白名单由 OpenAPI 生成，全是 GET、不带路径占位符、排除非 JSON 与助手自身；
   写操作一个都不放行——写必须走「出方案 → 人确认」。
2. **以当前用户的身份调**：用他的身份签一个短期令牌发给自己，**完整走一遍依赖链**，
   角色与参数校验真跑一遍。不存在「助手有特权」。
3. **走进程内的应用**（TestClient），不依赖网络与端口。

### 这块实测踩了三次，每次都改了设计

1. **第一次：它把轮次预算烧在试参数上。** 4 轮上限，它先猜错路径（按模块名猜 `/nutrition/candidates`，
   实际是 `/calibration/candidates`）、被白名单挡回、再试、又吃一个「缺 on_date」的 422……
   结论还没出来就用完了。改了两处：轮次上限默认从 4 提到 8（有了 call_api 之后试探是正常行为，
   这个上限是「别失控」的保险而不是预算），错误信息里带上「这个接口需要哪些参数」。
2. **第二次：还是烧完。** 日志显示它在**按日期×餐次扫**——想找哪天有抽样候选，
   就一天一天地换参数试。于是加了 `list_read_apis`：把「路径 + 必填/可选参数」一次给全，
   它就不用靠吃错误来学。顺带在空结果上加了一句「别一个日期一个日期地扫」。
3. **第三次：给了清单还是扫。** 它先用 `list_read_apis` 摸清接口（这一步生效了），
   然后照样一天天扫。于是加了通用的防抖：**同一个只读接口一轮里最多连查 3 次**，
   到点直接告诉它「扫不是办法，把已查到的整理给用户，或者问他想看哪一天」。
   加上之后它当轮就给出了正经答案：本周可抽的候选只有午餐那一餐、4 道菜、附单份理论值。

这三次迭代留下的分工很清楚：**手写工具管「深度」**（写操作，要确认、要撤回），
**`call_api` 管「广度」**（只读查询）。而「广度」的代价是探索，所以必须给它足够的信息
（接口清单与参数）和一条止损线（重复调用上限），否则预算都花在试探上。

## 模块 23 · 助手的写操作扩到「改、删、撤回」

### 做了什么

原来只有两个写工具（新增食材、新增菜品与配方），现在是六个：新增/修改/停用 × 食材、菜品与配方；
再加上「撤回」——已执行的操作可以一键改回执行之前的样子。为此在域层补了三样东西：
`reactivate_ingredient` / `reactivate_dish`（撤回停用要用，原来「停用」是单程的）、
`update_*` 与 `deactivate_*` 的 `audit_note` 参数（留痕要能标出「经助手提议、本人确认」）、
以及两个影响面计数（这个食材被几个配方用着、这道菜被几天供应过）。

### 撤回为什么做成「执行时记下来的步骤」

撤回要把数据改回**执行之前**的样子。最省事的想法是「执行完再看一眼数据库里当前是什么，
反着写回去」——但那是事后推断，中间只要有人插一脚就会写错。
所以让 `execute()` 在执行的当场返回「撤回要做的事」（一串 `{tool, payload}`），随方案落库。

好处是撤回不用为每种操作各写一套代码：撤回就是**把那些步骤用同一个执行入口再跑一遍**。
`update` 的撤回是写回旧值，`deactivate` 的撤回是重新启用，`create` 的撤回是停用（软删）。

### 两条不许越过的边界

1. **别人之后又改过，就拒绝撤回。** 数据在执行之后被改过的话，撤回会把那一次改动一起抹掉。
   用 `audit_logs` 判断「`decided_at` 之后有没有新的留痕」，有就拒绝并让人手工核对。
   宁可麻烦一点，也不做静默覆盖。
2. **没有物理删除。** 助手能做的最狠的事是停用（软删除），而且它可撤回。
   域层本来就没有物理删除的口子，助手也够不到。

### 三个踩到的坑

1. **CHECK 约束不会自己更新。** 状态枚举加了「已撤回」，但数据库那条 CHECK 还是建表时的取值，
   撤回时在数据库层被挡下来（表现是 500）。`autogenerate` 不比对 CHECK 内容，
   迁移里必须显式 drop + create。这条值得记住：**枚举加值 = 迁移里要改约束**。
2. **`Decimal("150.000").normalize()` 会变成 `1.5E+2`。** 模块 20 写的显示函数一直有这个 bug，
   连模型看到的数字都是科学计数法（「标准份量 1.5E+2 克」）。改用 `format(value, "f")`。
3. **测试清理撞外键。** 新用例建了带配方的菜品，清理时先删食材会撞 `recipe_items` 的 RESTRICT。
   顺序要是：营养结果 → 菜品（配方随菜品 CASCADE）→ 食材。

### 一次操作失误，也记在这儿

我想回退一个迁移，敲了 `pnpm db:downgrade`——那是 `alembic downgrade base`，
把**开发库**整个清空重建了。数据是可再生的（`db:seed` + `db:compute` 恢复），
部署库与 git 没受影响；但这是我自己该避免的（想回退一级应当是 `downgrade -1`）。
记在这里是为了下次直接用对命令。

## 模块 22 · AI 助手加流式输出

### 为什么不做「假的流式」

最省事的做法是：等模型整段回完，再在界面上按字打出来。看着像流式，其实用户还是要先干等
八到十几秒——那正是要解决的问题。所以走模型侧真正的增量（`stream: true`），
实测一次带工具调用的提问：**4.0 秒先出工具结果、5.0 秒起逐字出文字、6.5 秒结束**，
期间推了 150 个文字片段。等的过程中界面也不是死着：先显示「正在思考……」，
工具一跑就变成「正在查 看板指标……」，查完立刻把结果列进对话。

### 一件值得单独说的事：实现只有一套

加了流式之后最容易走偏的做法是「再写一个 `chat_stream`」——两份几乎一样的循环，
以后往其中一份加了东西、忘了另一份，就会出现「流式那版忘了落库」这种只在一条路上发生的 bug。
所以反过来做：`chat_stream` 是唯一的实现，**非流式的 `chat()` 就是把流抽干、取最后一个事件**。
原来那些用例一行没改，跑的还是同一套逻辑。

### 两个踩到的细节

1. **工具调用的参数在流里是碎片。** 第一片带 id 与函数名，参数一个字符一个字符地来
   （`{"days"` / `: 7}`）。不攒起来就会拿到半个 JSON——而半个 JSON 的后果很隐蔽：
   参数字典解析成空，工具以「没有参数」的方式静默跑错。为此单独写了累加器与用例。
2. **nginx 会攒一段再发。** 响应头加了 `X-Accel-Buffering: no`，否则流式在反代后面
   又变成「一次性到达」，白做。另外流式响应里自己管数据库会话：`Depends(get_session)`
   的生命周期跟着请求走，而流要等生成器跑完——不赌框架的时序。

### 顺带清掉的两处

- 抽屉里的「历史对话」原用了 antd 的 `List`，而当前版本已把它标为废弃——
  为一个「几条历史」引一个待替换的组件不划算，改成自己摆的一小块列表。
- 表格 `rowKey` 用下标是废弃用法（行序一变会错位），改成显式的行 key。

### 端到端用例差点白跳过

新加的那条「真实对话」用例先查状态再登录，而状态接口未登录返回 401，
`enabled` 读出来是 `undefined` → `test.skip(!undefined)` 恒为真 → 用例**永远被跳过**、
看着还是绿的。改成先登录再查状态。这类「跳过也显示通过」的坑值得记一笔：
跳过不是验证。

## 模块 21 · AI 助手（阶段二：写操作、确认卡片、对话留痕）

### 用户定的两条

「确认弹出卡片、对话内容保留审计」。第一句决定写操作的形状，第二句决定要加三张表。
两件事其实是一体的：方案要跨刷新存在、事后要能查「谁确认的」，就必须落库。

### 为什么是「方案」而不是「确认框」

最直白的做法是：模型调 `create_ingredient`，后端先弹个框问用户要不要执行。
但对话框是**界面**的事——接口层面还是「一次调用就把数据写了」，换个前端（或外部 agent 调用）
就绕过去了。所以做成**方案**：写工具的调用只落一条 `assistant_proposals`（PENDING），
`execute` 只在 `confirm_proposal` 里被调用。这样「没确认就写不了库」是接口的性质，不是界面的性质。

方案里存两份东西：`payload`（确认时执行的参数）与 `preview`（给人看的字段、提示）。
刻意不合并——两份分开，才能保证「页面上看到什么，执行的就是什么」，
而不是「页面显示一套、执行时再拼一套」。卡片上还带一句「确认之前什么也没有写进系统」，
因为模型很容易说成「已经建好了」，那句话得由界面兜住。

### 三条踩到的东西

1. **消息顺序不能靠时间戳。** 同一次提问的用户消息与助手回复写在同一个事务里，
   `created_at` 一模一样，再按 UUID 排就是随机的——对话会前后颠倒。
   加了会话内 `sequence` 自增序号，并把消息计数与序号的推进放在同一个函数里，避免两处各推一次。
2. **执行失败要落痕。** 第一次写的时候只接了 `AppError`，而参数校验失败抛的是 pydantic 的
   `ValidationError`，它直接冒成 500，「方案执行失败」这件事在库里查不到。
   现在两种都接住，方案留在 FAILED，错误信息取 pydantic 的字段定位（「category：取值无效」），
   而不是 `str(异常)` 那一长串。
3. **测试差点打到真模型。** 用户把云端 key 配进 `.env` 之后，两条「未接模型」的用例
   开始真的发请求出去（既花钱、结果也不可复现）。这不只是改断言的事——**任何**忘了注入
   脚本化 provider 的用例都可能联网。所以加了一条 autouse 的「一调就报错」的默认 provider：
   测试里结构上不可能碰到真实模型，需要真行为的用例再显式覆盖它。
   那两条写死的用例改成「状态接口说的与配置一致」（两种环境都成立）。

### 审计怎么查

抽屉里加了「历史对话」：本人看自己的，食堂管理员与学校管理方可以查阅全部。
每条对话能看到消息、助手调过哪些工具、提过哪些方案、以及方案的最终状态。
确认执行时走各业务域自己的 service，所以留痕与页面录入完全一致，
只是在备注里多一句「经 AI 助手提议、由本人确认后创建」——审计要能分清人和助手。

这一版能新增、不能删改：删除类工具要等更严的闸门（先预览影响面、再二次确认）才谈得上。

## 模块 20 · AI 助手（阶段一：只读问答）

### 目标与边界

用户想要的是「系统自带一个 AI，直接跟它对话就能完成操作」。这事分两种形态，差别很大：

- **外部 agent（Codex 这类）来操作**：不用做界面，工具层 + 一个令牌就够；
- **系统自带 AI**：要三样东西——模型接入、工具层、对话界面。

用户要的是后者。做的过程中把范围切成了三段：**阶段一只读**（查食材、配方、某天的菜单、
看板指标、最近采集），阶段二写操作 + 确认卡片 + 审计，阶段三批量与文件（把 Excel/照片整理成配方）。

先做只读不是保守，是算过的：助手写错东西会进历史、影响预测与公开大屏，擦起来要一条条改；
而只读问答零风险、当天就有用。这条边界写成了代码——`assert_read_only()` 会在工具注册表里
发现写操作时直接抛错，并有一条测试盯着它。

### 三个设计选择

1. **工具层直接调 service，不绕 HTTP。** 权限、事务、口径与界面上操作完全一致，
   不存在「同一条规则两处各写一遍」。同一套定义以后包一层就能给外部 agent 用（MCP），不用重写。
2. **模型接入走 OpenAI 兼容协议。** 一开始按需求里「数据不出校」把校内端点当成正式选择；
   后来用户明确说这条可以去掉、就用云端模型，于是改成「云端与校内共用一套配置、按需选」——
   换模型只改环境变量。**未配置时返回 503 并说明该配什么**，
   界面显示「未接模型」——绝不摆一个点了没反应的输入框（这是那次「注册接口 403 要说人话」
   同一条原则）。
3. **身份用当前登录用户，不额外提权。** 助手能看到的，就是这个人自己能看到的数据。

### 提示词里写了三条死规矩

只依据工具返回作答、**不许自己估营养值或金额**、缺项就说缺项并带上口径。
这个系统的可信度建立在「每个数都能回溯」上，助手不能成为例外——它最容易犯的错
恰恰是「凭常识给一个像样的数字」。

另外：工具的业务错误（菜名找不到、日期格式不对）**回给模型**让它自己改，而不是抛成 500
把整轮对话打断。模型自己纠错比我们猜它想干什么可靠。

### 测试怎么分层的

模型是外部服务，测它等于测别人的接口。所以：

- **工具层用真实数据库**：查出来的必须是库里种着的食材、菜品、菜单与指标。这一层是
  「助手说的话有没有依据」的根，不能用假数据糊过去；
- **对话层注入脚本化的 provider**：验的是我们自己的东西——工具调用怎么派发、
  业务错误怎么回给模型、轮次上限会不会兜住、未配置模型时是不是如实说不可用。

真实模型的连通性只能在部署环境里手动验（配好 `ASSISTANT_*` 之后问一句「今天吃什么」）。

### 会话不落库

历史由前端带最近 8 轮，服务端无状态。取舍：没有会话表就没有迁移、也没有
「谁的对话别人能不能看」的问题；代价是不能「接着上次继续说」。等真的要审计对话内容时再补。
工具调用会写日志（哪个用户、调了哪个工具、参数是什么），排查够用。

## 模块 19 · 批量排菜单与一键导入

### 要做什么

用户的原话：能批量生成一段菜单（例如 12 月 3 日到 5 日、12 月 7 日到 17 日），
生成之后可以一键导入当日菜单。做法：`批量生成` 只算、不落库；`一键导入当日菜单`
按日期区间把每一天最近生成的那一版写进当日数据。分两步是因为这一批是十来天的菜单，
落库之后每一天都会被采集页与大屏读到，想改要一天天改——先看一眼更稳妥。

界面上没有新增导航项：「单日」与「批量排菜单」是同一件事的两个粒度，用页面上的模式切换。

### 排出来是「A、B、A、B」

第一版跑 7 天，结果是两套菜单交替出现：

```
12-14 馒头、番茄蛋汤、胡萝卜炒鸡蛋、醋溜白菜、凉拌黄瓜、清炒西兰花
12-15 土豆炖牛肉、紫菜蛋花汤、米饭、蒜蓉油菜、干煸豆角
12-16 馒头、番茄蛋汤、胡萝卜炒鸡蛋、醋溜白菜、凉拌黄瓜、清炒西兰花   ← 同 14 日
```

原因不复杂：每天只排除「昨天」那 5~6 道，剩下的十几道里**最优解是同一个**，
于是求解器每天给出同样的答案。约束条文上没毛病（相邻两天确实没有重复的菜），
但这不是轮换，是一段只有两种菜单的菜单表。

解法是加一项**均衡偏好**：这一批里已经排过的菜，排得越多越不该再出现
（`PlanWeights.variety`，归一化后与成本、受欢迎度同量级，取 0.35）。
它是软的、压不过营养与预算，只在「都行」的时候起作用。加上之后 12 天排出 12 种组合。

### 主食一天排两份，第二天就没得排

第二版跑 12 天，中间有一天「排不出来」，而且原因说不清（求解器只给了「约束互相冲突」）。
查下来是：前一天排了**米饭 + 馒头**（`CATEGORY_MAX[STAPLE]` 允许 2），
而菜品库里主食只有这两种，于是第二天「同一道菜不连续两日重复」把它们全排除了——
主食一份都不剩，模型无解。

这是个通用问题（单日排菜单同样会把后一天堵死，端到端用例里也撞见过一次），
不是批量独有的。改成**主食每天只排一份**：食堂本来就是一天一种主食，
限制它不损失什么，却让「不连续两日重复」在只有两种主食的库里真正成立。

顺带补了一条诊断：某一类菜被排除光时要说出来（「主食类的菜已经一份都不剩」），
而不是笼统地说「约束互相冲突」。

### 人次与份数量级对不上

端到端用例又一次失败，这次的原因很值得记：某天的人次是 180，而份数按历史预测是 300~900 份，
两者差着一个数量级，折算出来的「人均油盐糖」被放大到任何菜单都超上限，于是排不出来。
而那 180 人次是**测试自己录进去的**（用例为了干净挑在将来某天录了一餐）。

处理方式：**不事先拦**，只在排不出来之后补一句说明。
一开始写成事先的门槛（「平均份数超过人次就拒绝」），结果误伤了能排出来的情况——
量级偏大时求解器可以靠挑低盐的菜把菜单排出来，事先拦掉等于把能用的菜单也挡了。
改名 `servings_mismatch_note`，只在失败路径上拼进错误信息里。

同时把端到端用例的耦合去掉了：需要人次稳定的用例，自己先通过接口录一餐把
「最近一次采集的人次」铺成与预测份数同一量级（`e2e/helpers.saveCollection`），
不再依赖别的用例留下的数据。

### 两个过程教训

- 端到端用例失败先看**是不是环境**：有一轮 20 条用例报
  `net::ERR_CONNECTION_REFUSED` 与「Failed to fetch dynamically imported module」，
  那是 vite 中途掉线，与用例本身无关。干净重跑一次全绿。
- 端到端用例不要依赖「库里现在没有数据」这种前提：同一个库被反复跑，
  昨天的「将来日期」今天就成了过去，别的用例写进去的采集记录会变成
  我这条用例的输入。需要什么前提就自己铺（`saveCollection` 就是为此加的）。

## 模块 18 · 同步至当日数据

### 起因：生成的菜单没人接住

用户问的是「我生成了明日菜单，第二天系统会自己把它放进采集页和大屏吗」。查完代码的答案是**不会**：
生成只写 `menu_suggestions`（推荐快照），而采集页的「当日供应菜品」与公开大屏读的是 `menu_days`，
两者之间没有任何连接——菜单日全系统只有一条写入路径：**采集页提交**。
实测次日的状态：采集页列出全部 20 道菜、一个都没勾、提示「这一天还没有确认菜单」；大屏「未安排」、0 张卡。

这不是 bug，是需求假设过时了：需求写「菜单日不单独维护，勾选即写入」时，
前提是「排菜单只发生在采集页里」。多了明日菜单生成之后，前提不成立。

### 改法：把「采纳」换成一个真正落库的动作

「采纳这份菜单」只是改一个状态位，界面之外什么都没发生。改成**「同步至当日数据」**，
一次做三件事：写那一天的菜单日（带计划份数）→ 按配方算单份营养 → 记为已采纳。

**为什么必须连营养一起算**：大屏只展示有营养结果的菜。只写菜单日的话，
第二天早上大屏仍然是空的——这一步不做，改动等于没做。

**为什么读快照而不是重算**：同步要落的是人当时看到并确认的那一版。
重算会算出可能不一样的结果（菜品轮换、排除规则都随时间变），那就不是同步，是悄悄换一份菜单。
为此在推荐快照里把「这一版是按哪些份数评估的」也存下来（`planned_servings`）。

### 三个决定

1. **计划与实际共用一张 `menu_days`**，不新开计划表。采集提交之前它是「计划供应」，
   之后是「实际供应」；分野靠两个事实判断（有没有计划份数、有没有当天采集记录）。
   两张表并存迟早会打架。
2. **采集提交保留计划份数**（覆盖前按菜取回来），因此事后能对上「计划 812 份、实际做了 700 份」。
3. **已经录过采集的那一天，同步被拒绝**并说明该去哪儿改——菜单以实际供应为准，
   把计划盖上去等于抹掉当天真实发生的事。

### 采集页跟着改：候选清单始终是整份菜品库

早先的逻辑是「有菜单就只列菜单上那几道」，于是**菜单一旦排好，临时加菜就没地方勾**——
而临时换菜在后厨是常态。现在整库都列着，菜单上的排最前、标「计划」、预勾选，
出餐份数的输入框把「计划 812 份」当提示摆着。用户的原话是「当然依然支持自己勾选修改」。

「计划」这个标记只在**采集提交之前**出现：提交之后菜单日写的是实际供应，
再给每道菜挂「计划」等于把实际做的事说成计划做的事。

### 大屏的时序口径

用户点明了这件事：**采集要到一天结束才录，大屏从早上就开始显示**。
所以大屏上「采集之前就存在的数据」= 菜单 + 单份营养（同步时就有了）；
油盐糖、食物种类那几项来自采集记录，采集之前如实显示「暂无数据」。
不拿昨天的数顶上、也不用推算值冒充实测值。

顺带给大屏加了 `?date=` 参数（只用于回看与演示）：排菜单的人要能当场看一眼
「明天的大屏长什么样」，而不是等到第二天早上才知道。挂机的大屏不带这个参数。

### 顺手修掉的一个 500

端到端用例撞出来的：求解器解不出来时抛的 `InfeasibleError` 不是业务异常，
直接冒成 **HTTP 500**，界面上只剩一句「服务器内部错误」——而求解器其实已经算清了卡在哪条约束上。
现在在 service 层翻译成业务错误（422）原样带出原因。

同时补了一条诊断：份数由预测给定之后，「少做点」这条退路没有了，只能换菜。
所以诊断要按「最少几道菜的合计」算——实测那句话是「按最少 4 道菜算，食盐合计已达 6.35g，
超过上限 5.000g」。**这是份数外接之后模型自由度变小带来的新边界**：
就餐人次填得远小于预测份数时（份数是按历史预测的），人均油盐糖会被放大，
那时候换菜也压不下去，系统只能如实说排不出来，而不是给一份超标的菜单。

## 模块 17 · 明日菜单与采购（合并「菜单推荐」与「采购预测」）

### 改了什么

侧边栏「日常运行」从 4 项变成 3 项：**明日菜单与采购** / 每日采集 / 抽样纠偏。
`/admin/menu-plan` 一页给出三块内容：

1. **明日菜品推荐**：菜品集合 + 营养差距 + 推荐理由，**不列份数**；
2. **明日食材采购建议**：采购量（公斤）+ 单价 + 金额 + 合计 / 预算，按金额从大到小排；
3. **依据与校验**（默认折叠）：每道菜的份数与依据、回测 MAPE、节假日日历、当天已生成的菜单记录。

后端新增 `menuplan` 域（`POST /api/v1/menu-plan/generate`），一层薄编排：没有自己的数据表，
只把推荐、预测、采购按**同一批菜**对齐。`/admin/forecast` 与 `/admin/recommendation` 保留为跳转。

### 关键判断：份数用预测的，不用推荐自己算

改之前系统里有**两个**对「明天做多少份」的估计，合到一页就会正面撞上：

| | 怎么来的 | 强项 | 短板 |
| --- | --- | --- | --- |
| 推荐份数 | 最近一次采集人次 × 0.9~1.1，在营养约束下解出来 | 与营养、成本自洽 | **不含日历修正**，不知道明天是不是放假 |
| 预测份数 | 最近 6 个同星期几的历史平均 × 日历修正 | 含节假日与调休、含真实波动 | 与营养目标无关 |

**结论：菜品组合与营养结构来自推荐，份数用预测。** 理由是采购恰恰在放假与调休那几天最需要准
（买多了浪费、买少了不够），而推荐份数恰恰在那几天最不准。

### 踩到的两件事

**1. 「推荐要份数、份数要菜单」是个假的死循环。** 份数进入推荐的营养评估（人均供给 =
Σ 单份营养 × 份数 ÷ 人次），看起来必须知道菜单才能算份数、算完份数才能选菜。
实际上预测是**逐菜独立**的——不依赖菜单——所以可以先给全部候选菜预测份数，再拿这份份数去选菜。
真正需要保证的是「预测的候选集」与「推荐的候选集」是同一批，否则会出现「预测了但没参与推荐」
或「推荐了却没有份数」的错位，为此加了 `candidate_dish_ids()` 作为两边共用的入口。

**2. 营养区间当硬约束会无解。** 实测这套配方蛋白供能比约 18%，而指南区间是 10%~15%，
于是「能量 ≥ 720 千卡」与「蛋白 ≤ 30 克」互相排斥，两条都当硬约束就是无解。
改为：**油盐糖上限、预算、道数、不连续重复、烹饪方式比例仍是硬约束**，
能量与三大营养素按「偏差最小」求解，差距表逐项给出「差多少、往哪个方向」。

### 一并修掉的成本口径 bug

单价是「元/公斤**市品**」，早先算成本时乘了可食部，把成本算低：
合计低 6.25%，清蒸鲈鱼低 42%，鸡腿烧土豆低 27.7%，清炒西兰花低 16.1%。
预算约束因此偏松。修法是去掉那一步乘法，并把口径写进 `ingredients.unit_price` 与
`seasonings.unit_price` 的模型注释、界面上表头标「元/公斤市品」——
这个 bug 的根因就是模型里没写单价是什么口径。

### 没有丢的功能

合并两页时容易被顺手丢掉、但都保留了的：**采纳 / 否决（否决必须写原因）**、
能量目标「尚未核实」的标注、缺单价的提醒、回测与日历核对入口、当天已生成的菜单记录。
预测结果也会随生成一起落库（只落入选的菜，不是整个候选池），
`forecasts` 表因此不会因为合并而变成一张没人写的表。

## 模块 16 · 菜单推荐（M6）

- 用整数规划（PuLP + 自带 CBC）而不是启发式：为了让「满足全部硬约束」这句话**可验证**。
  **PuLP 锁在 2.x**——4.x 不再自带求解器，`listSolvers()` 是空的，装上去会直接跑不起来。
- 三条踩出来的经验：区间中点也要进目标函数（否则求解器一路踩边界，交出一份「刚刚好达标」的菜单）；
  成本项量级比营养偏差大，等权时会把营养挤到边界（默认权重成本取 0.3）；
  要有菜品类别的数量上下限，否则会给出「两道汤 + 三道蛋菜」这种营养挑不出毛病但不是一餐饭的结果。
- 目标区间两条口径：能量与三大营养素按餐次占比折算（午 40%），油盐糖取每日上限不折算——
  按 40% 折算的话午餐食盐上限是 2 克，现有任何五道菜的合计都在 4 克以上，模型必然无解。
  真实差距（按折算应 ≤2 克、实际 4.5 克）在差距分析里如实报出。

## 模块 15 · 消耗量预测（M5）

- **同星期样本不足时退化为「全期平均 × 星期几规律」**，而不是放弃预测。轮换菜单里一道菜
  每四五天才出现一次，严格只认同星期几的话一多半的菜都没有预测；而直接用全期平均，
  周末会高估一倍以上（周末在校人数只有工作日的四成多）。实测这一步把回测 MAPE 从 37% 拉回 7.7%。
- **调休上班日要换基线**：调休那天多半是周末，拿周末基线乘系数是不对的，要按工作日的历史估。
- **节假日日历由迁移写入**，不是种子数据。它是参考数据（国办发明电〔2025〕7 号的 33 天放假 +
  6 天调休上班），生产环境也该有；写成种子就变成「演示数据」了。

## 模块 14 · 采集页离线队列

- 只把**网络层失败（0 / 5xx）**当离线。业务错误（4xx，例如日期已存在）不能进队列——
  排队重放一百次也不会成功，只会盖住真正的原因。
- 同 (日期, 餐次) 只留一条：离线期间改了几次，补交的是最后那一版。
- **TanStack Query 的 mutation 必须设 `networkMode: 'always'`**：默认模式下断网时变更会暂停在
  内存里等联网重放，既不进 localStorage 也不可见，界面看起来像「点了没反应」。

## 模块 12 · 三层校准的第二、三层

- 第二层从「当日比值」改成**按烹饪方式拟合历史系数**：每天一个方程，未知数是各烹饪方式的偏置。
  用**带岭项的非负最小二乘**求解（岭项罚向 1，因为「没有偏置」时系数本来就是 1；
  非负保证系数不会算出负用量）。窗口少于 21 次采集、或某类调料只有一种烹饪方式在用
  （只有一个未知数）时，退化为整餐一个比值并如实标注，不硬解出一组没有依据的数。
  当天总量因此从「乘数」降级为**校验项**：偏差超 10% 提示核对——这通常是漏记了一道菜或总量抄错。
- 第三层抽样反推调味料系数，系数超出 `[0.5, 2.0]` 判为疑似配方有误、**不套用**。
- 三层值并存不覆盖；大屏与看板取「抽样 > 校准 > 理论」中证据最强的一份，并标明来自哪一层。

## 模块 13 · 采集页与抽样页

- 校准残差超阈值时回写异常标记，让「这天数据可能不对」在采集页上看得见，而不是只躺在计算日志里。

## 导航重构与 PWA 提示条（未计入模块编号，但都改了行为）

- **导航按使用动线分三块**（数据看板 / 基础数据 / 日常运行），不按模块名归类：
  打开系统第一个问题是「今天怎么样」，而不是「我要去哪个模块」。
  路径保持扁平，`/admin/dashboard` 等旧地址保留为跳转。
- **PWA 提示条**：`registerType: 'prompt'`，有新版本弹提示、点了才刷新，并每 30 分钟主动检查。
  静默换版会让用户在半途被换掉一版界面，比不更新更糟。

## 模块 4 · 种子数据的收敛与轮换锚定

种子脚本必须是**幂等且收敛**的：

- 按**自然键认领已有行**（例如 `daily_logs(date, meal_type)`），而不是无脑插入——
  否则第二天再跑一次就会撞唯一约束。
- **历史窗口收敛**到固定天数，不随「今天是哪天」无限增长。
- **菜单轮换锚定到固定纪元日**（`_ROTATION_EPOCH`），而不是锚到「今天」：
  否则同一天跑两次、或隔天再跑，同一日期对应的菜会变，端到端用例与人工核对都会跟着漂。
- 端到端用例**不要写死菜名**（菜单是轮换的），也**不要假设「最新的菜单日就是今天」**
  （库里可能留着端到端造出来的未来日期数据），统一用 `tests/helpers.today_local()`。
- 测试跑完要把库还原：先记基线主键，结束后删掉基线之外的行，**再重灌一次种子**。
  只删新增行拉不回「测试改动过的种子行」（例如配方版本递增），而种子是收敛的，重跑即回到定义状态。

## 模块 1~11 · 早期决定

- **接口契约自动生成**：FastAPI OpenAPI → `packages/api-client`，
  CI 中重新生成并断言无 diff，接口改了却忘了同步类型会直接挂。
- **主键统一 UUID（应用层生成）**；日期类表加业务唯一键使离线重放天然幂等。
- **枚举用 `VARCHAR` + Python Enum + CHECK 约束**，不用 PostgreSQL 原生枚举：
  后者的改动成本高到让人不敢加值。
- **`dish_nutritions` 用 `caliber`（单份 / 人均）与 `value_type`（理论 / 校准 / 抽样）
  两个独立维度标记**，接口层禁止隐式转换；`computation_trace` 存配方快照、所用系数与公式版本，
  任何数值都能回溯到来源与计算过程。
- **改完前端必须重建容器**：本地 `pnpm dev` 是热更新，看着像「改完就生效」，
  而 8080 上的容器跑的是构建产物。
