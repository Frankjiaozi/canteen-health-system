## 1. 目标与当前事实

业务 API 应当独立完成数据体检、人数与菜品份数预测、菜单生成、营养与采购计算、正式发布和撤回。没有模型、没有 Agent、没有浏览器时，也可以通过 API 与自动化测试验证全部核心计算。

当前主分支已经有早餐菜品池、预测就餐人数、显式人数缩放、预算和排除约束、方案快照、发布冲突检查与撤回。下一轮先核验其正确性并补齐缺项，不重复重写整个系统。

当前只有 `/admin/agent` 一个助手。旧 `modules/assistant` 已删除；迁移 `a8e2144f17aa` 会删除旧助手表。不要重建另一套业务助手、提示词或模型配置。该迁移的回退只能重建空表，不能恢复旧聊天数据；实际迁移前必须保留可恢复备份。

## 3. 大任务 C：计算可靠性

### C01：把计算口径写清楚并让接口表达出来 ✅ 已完成

先列出实际公式、单位、数据来源与适用范围，再修实现。至少覆盖每份和整餐、人数和份数、预测和实际、市品和可食部、供给和摄入的区别。

- 菜谱原料数量 `quantity_per_serving_g` 是每份市品克数。
- 食材营养是每 100 克可食部；可食比例用于营养转换。
- 单价是市品元/千克；采购重量与成本不能再次乘可食比例。
- 钠 `mg` 与食盐 `g` 是不同指标，不能替换字段或直接相加。
- 理论、校准、抽样数据的优先级和来源应可追溯；当前优先级为抽样、校准、理论。
- 供餐营养不能直接表述成实际摄入；菜品种类不能直接等同食物种类。
- 当前目标配置包含未核实的能量来源和适用范围提示。查证适用规范后说明依据，不宣称大学食堂已经符合某一健康标准。

**验收**：提供一页计算说明和早餐、午餐、晚餐各一份可复算样例；接口中的目标依据、单位、缺项能支持前端如实展示。新增来源字段先走契约变更，不能静默改变旧字段意义。

### C02：营养和采购逐项复算 ✅ 已完成

固定菜谱、食材、价格与份数，用人工计算对照单菜、整餐、采购行及合计。金额使用 Decimal 和既定舍入规则；说明在哪一层舍入，保证行项目与合计一致。

以下仅是合成单元测试，不能当成真实菜品营养：某原料每份市品 100g，可食比例 0.8，每 100g 可食部蛋白质 10g，市品单价 10 元/kg。

```text
每份蛋白质 = 100 / 100 × 0.8 × 10 = 8g
每份采购成本 = 100 / 1000 × 10 = 1元
100份采购量 = 10kg，成本 = 100元
```

不能把成本乘 0.8 得到 80 元。缺蛋白质字段时应表示未知，不能自动得到 0g。零价格、零营养和缺值分别测试；缺价格时可返回已知项目小计并明确“不完整”，不能包装成完整总成本。

**验收**：覆盖单位换算、可食比例只应用一次、油盐糖、缺项、零值、非整数份数、金额舍入、重复原料合并，以及抽样/校准覆盖理论值。

### C03：人数与份数预测 🟡 部分完成

已核对：当前默认人数来自系统预测；用户显式输入人数时，现有份数缩放优先以系统预测人数为分母，缺预测时再尝试最近同餐次实际人数。`/menu-plan/generate` 的路由说明已同步，不再写“默认直接取最近实际人数”。

- 就餐人数与单菜份数分别预测，不能假设每道菜都等于人数。
- 仅使用目标日期之前、符合餐次条件的数据；回测也必须执行同样边界。
- 保留预测依据、样本日期、区间和节假日说明；样本不足时标记回退依据。
- 节假日经验系数和小样本回退属于假设，不能宣称为已验证准确率。
- 明确用户改人数时缩放哪些量；没有可靠基数时提示补充条件，不用除零或编造默认人数掩盖问题。

**验收**：固定历史和固定菜品条件下测试 800/1000/1200 人的缩放；分别测试无历史、少样本、换餐次、节假日、零实际、未来记录。若求解后更换了菜品，不要求整个菜单营养简单同比例，需分别验证预测缩放和最终选择。

### C04：菜单约束和营养差距 🟡 部分完成

- 保留早餐独立菜品池和饮品类别；午晚餐的昨日同餐次、当日其他餐次、用户排除规则分别测试。
- 主食允许重复的现有例外不能被统一去重逻辑误删。
- 区分预算、油盐等硬约束和营养软目标；不可行时解释约束冲突，不能把明显低能量方案展示成全面达标。
- 当前油盐糖求解使用日上限，差距展示按餐次份额计算。核对这种口径是否合适并统一解释；如调整规则，更新计算版本与样例。
- 食材缺营养、缺价格、可用菜品不足时给出机器可读问题及定位信息。

**验收**：早餐/午餐/晚餐、预算不足、无可用菜、全部排除、缺配方、缺价格等均有确定结果。针对历史低能量案例重新复现；旧日期旧版本数字仅作线索，不能当成本版本已验证失败结果。

### C05：生成、发布、撤回与版本 🟡 部分完成

生成会保存预测与建议快照，但不写正式菜单。正式发布继续复用 `publication.py` 的事务和校验；`/sync`、批量同步不得另写绕过保护的发布逻辑。

校验至少包括当前账号权限、目录/配方/价格快照、正式菜单版本、同日期餐次写锁和实际采集记录。冲突时返回 409，不覆盖其他人的新修改。

撤回应检查发布后的菜单是否仍可恢复，不能覆盖后续编辑或已有实际记录。保留发布和撤回审计，不把删除一条日志当成撤回。

当前代码计算版本为 `menu-plan-20261017.3`。若改变公式、缩放、求解或快照语义，评估升级该版本并拒绝不兼容旧快照；不要只改版本字符串而不补测试。

**验收**：重复发布不重复写入；旧快照、目录变化、其他人修改菜单、实际采集、并发发布、撤回冲突全部覆盖。当前没有承诺撤回接口可重复成功；若增加幂等行为，需明确契约与测试。

### C06：回测和质量报告 🟡 部分完成

提供按日期前推的回测样例，说明样本范围、餐次、误差计算、样本不足和零实际值处理。零实际不能伪造百分比误差。比较基线与改进算法时使用同一历史切分，不把演示数据上的结果宣传成真实食堂效果。

## 5. API 交付要求

现有路由和关键字段见 [共同契约](shared-contract.md)。保持业务 API 为唯一计算事实源，Agent 和页面不需要了解数据库结构。

每项接口变更提交以下内容：

1. 方法、路径、查询参数、请求体、角色与成功响应模型。
2. 新旧字段差异、是否兼容、空值意义、单位及舍入。
3. 正常、空数据、缺项、参数错误、权限错误、版本冲突的合法样例。
4. 对应测试、迁移、计算版本和恢复说明。
5. 运行 `pnpm gen:api` 后的生成类型，以及 Ethan 需要更新的消费位置说明。

新增字段优先可选且不改变旧字段语义。删除、重命名或改变单位必须先同步消费者；不得一边保留字段名一边把“每份”改成“整餐”。新字段在共同契约确认前标为提案，不能在两边代码中各自猜测落地。

建议把样例通过现有 Pydantic 模型或测试构造器验证，保证必填字段完整。不要手写一个只有几项字段的 JSON 却声称是可运行的完整 `MenuPlanResponse`。
