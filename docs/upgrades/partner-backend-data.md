# 协作者：业务后端与数据开发指南

你负责业务 API、数据库与计算，不需要判断页面视觉。使用 DeepSeek 辅助编码即可按本文的输入输出和验证执行。页面、Agent 推理与模型提示词由 Ethan 维护。

共同接口只维护 [shared-contract.md](shared-contract.md) 这一份。原架构与数据模型见 `docs/architecture.md`、`docs/data-model.md`，本指南说明本次升级增量与后续边界。

2026-10-17 整合保留了你方的业务助手、批量排餐、菜单同步与营养参考快照。`/sync`、`/batch/sync` 和 `/publish` 现在共用 `publication.publish`，不能重新写一个绕过目录快照、菜单版本或实际采集校验的同步实现。助手菜单/采集执行需要 `commit=False`，由卡片服务统一提交业务与状态；普通页面调用默认仍提交。调整该约定前请先跑 `test_merge_workflows.py` 和助手/采集回归。

新增三个同伴迁移随主分支保留；已有库先迁移，不自动重新灌种子。营养参考来源保留同伴的逐项字段与快照；菜谱、价格和供餐历史仍含演示资料，不能把来源更新解释成真实食堂经营数据。

## 工程边界

你可维护 `apps/api/**`、业务迁移与测试、业务 OpenAPI 和 `packages/api-client/src/schema.d.ts`。不要跨到 `apps/agent` 写模型编排，也不要修改 React 页面来适配不完整接口。

业务服务必须在 Agent 不运行、没有模型密钥时独立计算。公开大屏、采集、抽样、菜单、营养与采购全部由业务服务负责。Agent 对业务库没有读写连接，只能调用你提供的 HTTP 接口。

本次为了闭环，已经补上你后续应接管的业务文件：

| 文件/模块 | 当前职责 |
| --- | --- |
| `modules/menuplan/service.py` | 预测 → 约束求解 → 采购 → 快照；支持排除菜品与每人预算 |
| `modules/menuplan/schemas.py` | 原响应、新约束与发布请求/收据 |
| `modules/menuplan/publication.py` | 完整快照、目录指纹、版本核验与正式发布 |
| `modules/menuplan/readiness.py` | 同口径只读数据体检、可定位的缺项与阻塞原因 |
| `modules/menu/locking.py` | 同日期/餐次的 PostgreSQL 事务写锁 |
| `modules/menu/service.py` | 实际采集确认菜单也使用同一餐次锁 |
| `modules/recommendation/service.py` | 将用户约束交给求解器；已发布结论不能改写 |
| `modules/forecast/service.py` | 采购合计一致；同餐次预测和逐日无未来数据的回测 |
| `modules/nutrition/service.py` | 零预测/零实际不误报；零预测却有实际时相对偏差为空 |
| `app/dev_workspace.py` | 固定的本机独立演示库与测试库准备 |
| `app/preflight.py` | 不改数据的启动检查 |

本次业务结构没有新增表，不需要新增 Alembic revision。快照和发布收据保存在现有 `MenuSuggestion.nutrition_gap` JSON 中。后续如迁为专门的计划/版本表，先提供兼容读取或明确迁移方案，不可直接丢弃旧快照。

## 无需前端也能开发

安装 `apps/api[dev]` 后：

```powershell
# 在仓库根目录，Docker 已从系统菜单打开
pnpm db:up
pnpm demo:prepare
pnpm test:py
```

`test:py` 自动创建/迁移本机 `canteen_upgrade_test` 并运行测试。测试只允许库名以 `_test` 结尾，防止种子准备和清理覆盖真实输入。不要向测试库复制真实个人数据。

业务接口本身可用 `pnpm dev:api` 启动在 8000；交互文档 `/docs`，无需视觉模型即可在文档中校验 JSON。现有开发库需要已有账号与数据；若要完整示例，使用 `pnpm dev:demo`，业务接口为 8002，数据与原库分开。

演示库预置 20 道菜和 56 天合成记录。原 `canteen` 开发库目前菜品较少，某些约束无解是合理反馈，不能为让演示成功直接删除约束或往原台账灌假记录。

## 首版必须维持的业务语义

### 生成、采纳、发布是不同动作

- `/menu-plan/generate` 保存建议、预测与完整快照，不写正式菜单。
- 原 `/recommendation/{id}/decide` 只是给未发布建议记录采纳/否决。
- 新 `/menu-plan/{id}/publish` 才把确认的菜写入 `MenuDay / MenuDayItem`，记录计划份数、当前确认人和审计，并计算公开菜品的理论营养。
- 发布不创建 `DailyLog`、不伪造实际出餐和油盐糖，也不向供应商下单。

### 一套份数贯穿计算

菜品由整数规划选，份数由历史预测提供，采购按选中的菜乘以份数计算。用户指定人数时，当前采用明确标注的等比例情景调整，不能一边按 800 人计算营养、一边按旧人数汇总采购。

算法仍保留既有基线：星期与已核实日历修正、异常/替换日剔除、数据不足降级和说明。第二轮修正了午晚餐历史混用、目标当天进入人次基线、回测星期规律看到未来记录的问题；请保留 `test_history_boundaries.py` 回归。营养数值来源按证据区分，不得覆盖理论/校准/实测三个口径。

### 约束与金额

每人预算和排除菜品是请求参数，不得改全局配置后影响其他用户。同一道菜不连续两日重复与主动排除同时生效；理由要区分“昨天供应”与“用户要求”，不能把主动换菜说成历史事实。

营养区间是现有求解目标，部分油盐糖等为硬约束。不能把未达标建议说成“营养完全达标”。原资料的适用人群与大学食堂并不等同，详见 [营养目标口径](nutrition-scope.md)。目标附近的约束提示也必须与实际差距一致，不能把远低于下限说成刚好达标。

配方用量是克、市品重量；采购是公斤；单价是元/公斤市品，不额外打可食部折扣。成本参与求解时保留 Decimal 精度，不能先把单份成本过度四舍五入。采购合计等于展示的逐项金额之和；缺单价时金额不完整，必须保留警告。

## 发布的完整保护

1. 当前业务 Cookie 解析用户，角色与启停状态以数据库为准；只允许录入员/食堂管理员生成和发布。
2. 建议行 `FOR UPDATE` 防止重复确认与并发改状态。
3. 完整结果 + 配方版本 + 原料/调味料资料形成快照凭据，客户端不能伪造菜单内容。
4. 同餐次事务 advisory lock 与菜单版本校验，避免两个旧建议覆盖同一餐。
5. 已有实际采集则拒绝覆盖，即使版本相符。
6. 发布前再次核对配方、原料营养、价格与启用状态；生成过程中变化也需要重算。
7. 菜单、营养与审计在发布事务内提交。重复确认返回同一收据，不新增审计。
8. 常见写冲突/死锁返回 409，不能悄悄重试并覆盖其他人的结果。
9. 修改计算口径时升级 `CALCULATION_VERSION`；旧的未发布快照必须重算，旧的已发布收据依旧可重复读取。采购、营养和正式菜单均使用保存的 `planned_servings`，预测不足也不能在发布时另换一套数量。

数据体检接口只读，响应字段与生成候选口径一致：餐次、目标日期、昨日去重、主动排除都影响可用集合。单价为 0 是已知零价，不能当作缺价。无历史餐次不能借另一餐次数据伪造可预测状态；警告和阻塞都保留原数据定位入口。业务调用方不应把 `ready` 当作求解成功或来源认证。缺价警告在生成结果里只针对实际选中菜用到的材料，体检则可以报告所有可用候选的数据缺口。

不要新增一个“给 Agent 用、不需要登录”的管理员接口。Agent 没有特殊权限。不要从前端或模型接收确认人 ID、角色、最终金额或任意 SQL。

## 如何向 Ethan 交付新能力

每个能力提供：路由与方法、输入字段/单位/范围、正常响应、无数据响应、业务无解、无权限、冲突样例，以及一个可执行测试。

示例：如果新增“保持预算换一道菜”，不要只返回一句解释，应返回新业务方案 ID、选中菜与份数、采购明细、前后约束、营养差距与原因；Agent 再保存新版本，前端展示比较。模型不能自己计算采购数字。

改接口后运行 `pnpm gen:api` 并把生成物和源模型一起交付。不要手改 `schema.d.ts`，也不要让 Ethan 从日志里猜结构。以最小兼容变更推进，保留旧调用方式直到协商迁移完成。

推荐后续后端工作按价值排序：

1. 真实资料接入：本次已实现只读数据体检；下一步由人工核实配方、单价、营养来源和供应历史，补实际资料，不编造缺失数据。
2. 预测与计划的口径：评估人数缩放假设是否适合食堂的选菜供应模式，增加可验证的份数策略，不用语言模型替代数值计算。
3. 持久计划版本：若多页面需要共享方案，设计业务计划列表/详情与稳定版本；保留本次快照和重复确认语义。
4. 约束扩展：只有数据与需求明确后才加入食材供应、库存、过敏原、偏好等约束，并返回具体冲突原因。
5. 运营报告：给出真实聚合数据与来源，明确报告口径；当前已有 CSV、Markdown 和可离线打印的方案 HTML，服务端 PDF/Excel 另行实现，不混淆导出格式。

## 没有视觉能力的验收方式

无需看图判断页面。你只需要验证这些事实：

- 相同历史与约束可以生成可复核结果；排除 ID 不在新菜单内。
- 600 与 1200 人的情景在其他条件相同下，采购量随份数变化，金额与明细相符。
- 极低预算或候选不足返回 422 + 冲突方向，不是 500 或伪结果。
- 两个版本竞争发布，旧版本被拒绝；同版本重复确认不重复执行。
- 改配方、单价或原料营养后，旧快照不能发布。
- 学校管理方可以查看/核查，不能生成与发布。
- 已有实际采集的餐次不能被计划覆盖。
- 发布后 `GET /api/v1/public/board/today?on_date=指定日期` 有对应菜品和营养；没有伪造就餐人次。
- 原有营养、预测、采集与认证测试仍通过。

```powershell
pnpm test:py
pnpm lint:py
pnpm typecheck:py
pnpm gen:api
```

独立服务、前端和截图由 Ethan 最后联调。Git 使用功能分支，一次交付一个完整业务场景；数据库迁移与共享配置先对齐维护人，减少两人覆盖。

## 当前限制

仍是单食堂场景，没有多租户、真实食堂接入或自动采购。数据是来源未核实的现有数据或明确标注的合成演示；不能宣称已经验证节省金额、降低浪费或改善个人健康。模型真实调用需要配置后补测，不能把协作者的 DeepSeek 编码工具当成产品已接入模型的证据。
