## 0. 执行摘要

### 总体结论

这份系统的数据分层和可追溯设计整体是认真的，不是“几个页面直接拿 mock 数字”的演示壳：

- 营养快照有明确的外部平台、条目 ID、查询日期和 kJ 换算规则；
- 膳食指南的 4 项量化基准带原文引用；
- 理论营养、当日校准、抽样实测三类结果并存，并有 `caliber` / `value_type` 两个独立维度；
- 食材单价按“元/公斤市品”参与成本，没有错误乘可食部；
- 预测只使用目标日前历史，回测有独立切分；
- 菜单发布保存完整快照和版本凭据；
- 核心算法多数是纯函数，测试覆盖也比较充分。

但系统现在**还不能被称为生产可信**。主要不是因为公式写错，而是因为几处口径混用、输入缺失被当成 0、历史数据会被当前配方重写，以及部分目标值仍是未核实的演示配置。

## 1. 审计方法与限制

### 1.1 方法

1. 阅读需求、架构、数据模型、计算口径、预测质量报告和协作者数据目录；
2. 从 ORM 模型、迁移和种子脚本建立表/字段/数据来源清单；
3. 沿着营养、采集、预测、推荐、采购、发布、看板、大屏逐条追踪调用链；
4. 对当前开发库做只读统计，区分种子数据、测试残留和派生结果；
5. 运行针对性回归：`tests/modules/nutrition`、`forecast`、`recommendation`、`analytics`、`collection`，共 117 条用例通过。

### 1.2 限制

- 没有重新联网抓取中国食物成分平台；能确认快照结构和映射一致，但不能确认平台当前页面内容未被远端改动；
- 没有真实学校采购价格、真实菜谱和真实历史台账；
- 本报告区分“代码设计是否合理”和“当前演示数据是否能用于生产”；
- 当前开发库存在一些测试残留数据，本文只把它们作为环境卫生问题，不把它们当作种子定义。

## 3. 基础数据逐项审查

### 3.1 食材营养与可食部

**结论：来源设计合理，演示数据的来源标识可信度较高；生产前仍需逐条业务复核。**

证据：

- 快照来源写明中国疾控中心营养与健康所的食物营养成分查询平台，查询日期 2026-10-15：`apps/api/app/db/nutrition_reference.json:2-9`；
- 当前快照有 37 个条目，五个营养值和可食部都不是空值；
- 4 个单一成分条目用 `zero_filled` 明确声明“平台未列但物质本身不含”：食盐、白砂糖、芝麻油、大豆油；
- 种子写入 `data_source`、`source_version` 和 `note`：`apps/api/app/db/seed.py:220-279`；
- 计算引擎按每 100 克可食部 × 可食部用量计算：`nutrition/engine.py:174-231`；
- 当前开发库的 30 个 active 食材都有平台来源和条目 ID，除测试残留外未发现无来源的 active 食材。

需要注意：

- 这是 2026-10-15 的快照，不是实时查询；平台改版或条目更新不会自动反映；
- “来源合理”不等于“对某学校某菜品一定适用”，同名条目、均值条目和部位差异仍需业务确认；
- 当前数据库的测试残留中有 10 个 inactive 食材，`data_source` 为“端到端测试构造”；它们不在 active 列表中，但应在清洁环境中删除。

### 3.2 调味料营养

**结论：7 个条目走平台快照，1 个条目是明确的演示占位；结构合理，但“缺失”和“旧占位值”需要区分。**

证据：

- 8 个 active 调味料：大豆油、食盐、白砂糖、生抽、蚝油、玉米淀粉、豆瓣酱、陈醋；
- 蚝油在 `nutrition_sources.json:78-80` 中 `food_id` 为空，代码走 `DEMO_DATA_SOURCE`（`seed.py:241-249`）；
- 当前开发库的蚝油仍有 114 kcal、4g 蛋白等旧演示值，来源标为“演示占位值，待核对”；
- `_nutrition_values` 对无快照条目的新行只返回来源和备注，不返回营养字段；因此**新库中的蚝油营养会变成 NULL，而旧库会保留旧值**。这是一个“种子幂等但不收敛”的隐藏差异。

建议：

- 新鲜数据库和已有数据库应得到同一结果；对无来源条目要么显式清空营养值，要么把演示值集中在一个版本化占位快照中；
- 调味料的 `data_source` 在模型和 Excel 导入中是可空的（`seasoning/schemas.py:29`，importer 仍允许空），应至少与食材一样要求来源，否则会出现“有营养值但无法追溯”的 active 调味料。

### 3.3 单价与成本基础

**结论：单价字段的市品口径正确；但数据本身是演示值，不能支撑真实预算决策。**

证据：

- `Ingredient.unit_price` 和 `Seasoning.unit_price` 注释明确为元/公斤市品（`ingredient/models.py:38-45`、`seasoning/models.py:44-49`）；
- 成本计算直接 `quantity / 1000 × unit_price`，没有乘可食部（`recommendation/repository.py:47-91`、`forecast/service.py` 的 `build_purchase_list`）；
- 种子中所有单价都是硬编码演示值（`seed.py:286-319`、`353-362`）；
- 模型没有“价格来源、报价日期、供应商、有效期”字段，无法做生产采购审计。

结论：采购算法本身正确；基础价格不合格。接入真实价格时，建议新增结构化价格批次和报价日期，而不是继续把价格写在备注里。

### 3.4 菜品与配方

**结论：作为业务主数据模型是合理的；当前内容只是人工编制演示配方，不是真实学校菜谱。**

证据：

- 菜品、配方食材、配方调味料分表定义：`dish/models.py:27-110`；
- 配方食材用量是每份市品克数，调味料用量是每份克数；
- 种子 25 道菜、46 条配方食材、59 条配方调味料；
- 配方整体替换时递增 `recipe_version` 并写审计（`dish/service.py:286-327`）；
- 菜品必须有配方才能参与推荐（`recommendation/service.py` 的 `_candidates`）。

主要问题不是结构，而是历史不可变性：

- `recipe_version` 只是一个递增整数，没有 `recipe_versions` 快照表；
- 改配方会重算所有历史菜单日（`nutrition/service.py:177-190`）；
- 因此“昨天的营养结果”可能因为今天的配方修改而变化；
- 审计日志虽保留修改前后，但 `dish_nutritions.computation_trace` 在重算后写的是新配方快照，不能独立还原历史配方。

这是 P1 级可追溯性问题。建议增加不可变配方版本，历史营养结果记录 `recipe_version_id`，重算只能针对明确选择的历史快照。

### 3.5 膳食指南量化基准

**结论：4 项外部基准有原文来源；能量与三大营养素目标仍是未核实配置，不能等同于指南基准。**

证据：

- 食盐、烹调油、添加糖、食物种类数写入 `_STANDARDS`，带来源和原文引用：`seed.py:815-880`；
- 能量 1800–2000 千卡、早/午/晚 30%/40%/30% 在 `core/config.py:64-74`；
- `targets.py` 明确标注 `energy_verified=False`，并说明“待以《学生餐营养指南》等标准原文替换”；
- 供能比 10–15%、20–30%、50–65% 取自《中国居民膳食指南（2022）》的比例，但用演示的总能量反推克数。

结论：

- 食物种类、油盐糖的原文来源合理；
- 能量目标和人群适配尚未完成，不能把推荐结果表述为“符合学生餐营养标准”；
- 配置没有校验三项餐次份额之和为 1，也没有校验能量下限小于上限；错误配置可静默进入求解。

### 3.6 节假日与调休日历

**结论：日历来源合理，当前实现与 2026 年官方通知一致；但模型注释已过时。**

证据：

- 迁移 `efbc0c52196f` 按官方通知写入 33 天放假、6 天调休；
- 当前库查询到 33 个 `HOLIDAY`、6 个 `WORKDAY`；
- `load_holidays` 只读取 `is_verified=true` 的条目（`forecast/repository.py:28-34`）。

文档问题：

- `forecast/models.py:46` 注释仍说“内置的 2026 年日历全部是待核对”，与后续迁移和 `docs/data-model.md` 不一致；
- 这会影响维护者判断当前日历是否可信。

### 3.7 原始运行数据与输入边界

**结论：表结构基本合理，但“空值”被当成 0 是最严重的输入质量问题。**

证据：

- `DailyLogWrite` 把油、盐、糖默认成 0（`collection/schemas.py:86-88`）；
- 前端 `buildSavePayload` 也把空输入转成 0；
- `compute_theoretical_per_capita` 在人次为 0 时抛错（`nutrition/engine.py:576-590`）；
- 但 `DailyLogWrite.diner_count` 和数据库 CHECK 都允许 0（`schemas.py:85`、`collection/models.py:73`）。

影响：

- 未测量油盐糖会被当成真实 0，导致“低盐/低油”假象；
- 通过 API 直接提交 `diner_count=0`，保存采集时会进入人均计算并抛 `ValueError`，可能变成 500，而不是结构化业务错误；
- `leftover_ratio` 为空时按 0 剩余计算，虽然比把缺失写 0 好，但仍应明确“未测量”的语义。

## 4. 二级数据与算法逐项审查

### 4.1 理论单份营养

公式：

```text
食材贡献 = 市品用量 ÷ 100 × 可食部比例 × 每 100g 可食部营养
调味料贡献 = 调味料用量 ÷ 100 × 每 100g 调味料营养
```

代码：`nutrition/engine.py:185-285`。

审计结论：**合理。**

- 食材与调味料分开累计；
- 缺营养值按 0 参与加总但写入 `missing_nutrients`；
- 误差区间基准 15%，每缺一项加 5%，最多加 3 项；
- 纯函数不访问数据库，容易单测和替换；
- 价格不参与营养，可食部不参与成本，两个口径清楚。

### 4.2 人均摄入

公式：

```text
实际消耗份数 = 出餐份数 × (1 − 剩余比例)
人均摄入 = 单份营养 × 实际消耗份数 ÷ 就餐人次
```

代码：`nutrition/engine.py:576-595`、`nutrition/service.py:731-785`。

审计结论：**公式合理，输入边界需要修正。**

- `PER_SERVING` 与 `PER_CAPITA` 分开，未发现把三份证据重复相加；
- 看板在 SQL 中按“菜品 + 日期 + 餐次”先取 rank=1，再加总（`analytics/repository.py:86-154`），这一点正确；
- `diner_count > 0` 是人均存在的必要条件，但 schema 允许 0；
- `leftover_ratio` 缺失被解释为无剩余；如果实际未称重，应在界面标“未测”，而不是默认 0%。

### 4.3 第二层：当日闭环校准

公式：

```text
某餐某类调料实际总量
= Σ(各烹饪方式的配方推算量 × 该方法该调料的偏置)
```

代码：`nutrition/engine.py:300-550`、`nutrition/service.py:263-515`。

审计结论：**数学建模方向合理，工程边界有 P1 问题。**

合理之处：

- 不再用“当天总用量 ÷ 某一类菜推算量”这种无解算法；
- 使用 42 天窗口、至少 21 次采集、按烹饪方式分组、油盐糖分别拟合；
- 非负最小二乘 + 向 1 收缩的岭项；
- 样本不足或只有一种烹饪方式时退化为整餐一个比值并记录原因；
- 只缩放调味料贡献，食材部分不变；
- 当天总量作为校验项，偏差超过 10% 写入异常标记。

问题：

1. **目标日包含在拟合窗口内**：`window_start = on_date - 41`，`end=on_date`（`nutrition/service.py:309-310`），因此当天实际用量参与了系数估计；随后又用同一个当天数据做“校验”，残差不是独立验证，会偏低。
2. **历史配方不是历史快照**：`load_calibration_samples` 用 `dishes` 当前配方回算所有历史天的推算量。如果配方已改，历史实际用量与新配方不匹配，拟合出的系数不是当时的真实偏置。
3. **异常日没有在样本层过滤**：`load_calibration_samples` 读取窗口内所有 `DailyLog`，没有判断 `anomaly_flags`。人工异常日、系统残差日都可能继续进入下一轮拟合，存在误差循环。
4. **采样修正跨餐次**：`latest_sampling_corrections` 只按 `cooking_method` 和日期查询，不过滤 `meal_type`（`nutrition/repository.py:438-470`），同一烹饪方式在早餐的抽样可能被应用到晚餐。

### 4.4 第三层：抽样纠偏

公式：

```text
调味料整体系数
= (实测能量 − 食材推算能量) ÷ 配方调味料推算能量
```

代码：`nutrition/service.py:823-968`。

审计结论：**作为“能量差额全部归调味料”的可解释模型是合理的，但不应被理解为对所有营养素的独立实测校验。**

合理之处：

- 系数限制在 `[0.5, 2.0]`，超出范围不套用并标记疑似配方错误；
- 抽样值本身按 `SAMPLED` 落库，理论/校准值不覆盖；
- 误差区间由实测偏差决定，至少 5%。

问题：

1. 系数只由**能量**反推，却同时乘到所有调味料营养贡献上；如果抽样实测蛋白质/脂肪/钠的偏差与能量不同，二次应用会造成各营养素不一致。当前文档明确这是假设，应继续保持显式说明。
2. `latest_sampling_corrections` 取“最近一条”，但没有时效上限；多年前的抽样可能永久覆盖新的校准值。
3. 抽样记录有 `meal_type`，但方法级修正查询不过滤餐次；是“跨餐通用”还是“同餐生效”必须明确并写进契约。

### 4.5 证据优先级与陈旧值

代码：`app/shared/nutrition_values.py:17-57`、`nutrition/service.py:579-625`。

审计结论：**优先级本身合理，但缺少时效约束。**

- `SAMPLED > CALIBRATED > THEORETICAL` 的设计清晰；
- 同一菜品同一天的多份结果并存，不会覆盖；
- 问题在于推荐使用 `latest_per_serving_snapshots`，它会优先选择**任何日期**的抽样值，即使这个抽样已经非常旧；一个旧的 `SAMPLED` 可以永久压过昨天的新校准值。

建议增加“证据有效期”：例如抽样在 30 天内优先，超过后回到校准/理论；或把“旧证据仍优先”作为明确产品决策写入需求。

### 4.6 就餐人数预测

代码：`forecast/service.py:295-386`、`forecast/strategy.py:260-360`。

审计结论：**整体合理。**

- 同餐次、同星期几最近 6 个中位数；
- 排除法定假日、异常日、零人次；
- 放假目标日乘 0.45；调休上班日换工作日基线；
- 样本不足退化并标注；
- 不使用目标日或未来日。

风险：

- 0.45 是经验值，不是从真实数据估计；当前只覆盖演示数据；
- `EXCLUDED_FLAGS` 和 `is_anomalous` 在策略层存在，但实际 `load_diner_history`/`load_dish_history` 只要有任何 `anomaly_flags` 就排除，包括系统自动写的 `CALIBRATION_RESIDUAL`；代码意图与实际实现不完全一致。

### 4.7 单菜份数预测

代码：`forecast/service.py:211-293`、`forecast/strategy.py:170-260`。

审计结论：**基本合理，但节假日历史处理有重复折减风险。**

- 同星期最近 6 个平均；
- 样本不足退化为 `全期平均 × 星期几规律`；
- 只使用目标日前数据；
- 排除异常、临时替换、0 份记录；
- 回测按天重建历史，避免未来数据泄露。

问题：

1. `load_dish_history` 只排除异常/替换/0 份，不排除法定假日；如果同星期历史中包含一个已按 0.45 生成的假日样本，预测普通日会把基线拉低；预测假日又会再乘一次 0.45，形成双重折减。人数预测明确过滤假日，单菜份数预测没有做同样处理。
2. `weekday_profile` 用全部历史计算星期几规律，也会把假日样本混进 profile。
3. 质量报告已经说明只覆盖午餐、只覆盖演示数据；这是正确的限制，但不能把它当作生产准确性证明。

### 4.8 采购量与成本

公式：

```text
采购量(g) = Σ(每份用量(g) × 预测份数)
采购量(kg) = 采购量(g) ÷ 1000
行金额 = 采购量(kg) × 单价(元/kg 市品)
合计 = 各行金额按分舍入后相加
```

代码：`forecast/service.py` 的 `build_purchase_list`；成本来源 `recommendation/repository.py:47-91`。

审计结论：**口径正确，价格的来源不足。**

- 没有乘可食部；
- 按公斤输出，按金额排序；
- 缺价格时行金额为空，合计只包含已知价格部分并提示不完整；
- 单价是演示值，无法作为真实预算依据。

### 4.9 菜单推荐与三餐编排

代码：`recommendation/service.py`、`solver.py`、`targets.py`、`menuplan/service.py`。

审计结论：**求解器设计合理；油盐糖的日上限被按餐使用，缺少全天汇总硬约束。**

合理之处：

- 整数规划而不是启发式；
- 选中菜品数量、类别上下限、单一烹饪方式占比、食材种类、预算、油盐糖上限；
- 能量与三大营养素是软目标，避免和蛋白质供能比硬冲突；
- 份数由预测输入，不由推荐自己造；
- 晚餐避开午餐非主食；
- 早餐固定组合，午晚餐池子分离；
- 发布快照保存菜品、配方版本、采购结果和摘要凭据。

问题：

1. `targets.seasoning_targets` 直接把**每日**油盐糖上限作为**每一餐**的硬约束（`targets.py:102-123`）。三餐分别生成时，没有“当日三餐合计”约束；理论上三餐可以各自用到日上限。
2. 页面差距按餐次占比展示，但求解器使用每日上限，这是一项明确的双口径设计；它避免无解，但不能证明全天符合指南。文档已如实写出，产品层仍应决定是否接受。
3. 食物种类基准 12 种也被直接作为每餐下限（`targets.py:128-133`），而指南原意是每日至少 12 种；这是偏严格的“每餐 12 种”解释，需要确认。

### 4.10 看板聚合

代码：`analytics/service.py`、`analytics/repository.py`。

审计结论：**大部分聚合正确；一个核心 KPI 标签错误。**

- 趋势中的油盐糖总量按天汇总，人均按每餐各自除以本餐人次再相加，公式正确；
- 人均营养按“菜品 + 日期 + 餐次”取证后再相加，避免把三层结果重复相加；
- 达标率对 `unknown` 不计入分母；
- 浪费率按剩餐重量 / 出餐重量估算；
- **`avg_diner_count`**：趋势点 `diner_count` 是当天三餐人数之和（`analytics/service.py:184`），`build_summary` 再对这些日合计取平均（`service.py:307`）。该值现在明确展示为“供餐人次”，不再称为“平均每餐人次”。开发库实测 1,765，保留为日均三餐合计。

### 4.11 公开大屏

代码：`public/service.py`、`public/repository.py`。

审计结论：**修复前菜品的单份营养取值正确，但餐次/全天口径混用；现已按展示餐次收口。**

- `load_menu_day` 按午餐 > 晚餐 > 早餐选一个“主餐次”；
- 菜品卡使用该餐的单份营养；
- 修复前油盐糖、食物种类和 `diner_count` 使用同一天所有餐次的 `DailyLog`；
- 现已改为只读取 `menu_day.meal_type` 对应的采集记录和食物种类；无菜单时返回空实际值。

修复前开发库 2026-10-19 的异常表现是：大屏标题为“午餐”、展示 5 道午餐菜，但人次为 2,194（早餐 503 + 午餐 914 + 晚餐 777）。现在已新增测试，直接断言大屏人次、食盐和食物种类都属于展示餐次。

### 4.12 发布、撤回与历史快照

代码：`menuplan/publication.py`。

审计结论：**发布流程本身很稳健，历史营养仍不稳健。**

- 发布前校验快照 token、菜单 token、配方/原料/单价 token、菜品版本、已有采集和预算；
- 发布后在同一个事务中写菜单日、审计和发布回执；
- 撤回保留发布前菜单与 after token，能阻止覆盖别人改动；
- 这是本系统最扎实的边界之一。

不足：

- 快照保存的是配方版本号和 catalog token，不是完整的历史配方版本实体；
- 发布后再修改配方，普通营养重算仍可能改变历史菜单结果；
- 因此“发布快照可复核”与“历史营养不可变”不是同一件事，文档需要区分。

## 6. 风险清单与建议

### P0 · 会直接展示错误业务数字

#### P0-1 看板平均每餐人次

- 位置：`analytics/service.py:184, 307-315`
- 现象：每日三餐人数先相加，再按天平均；标签写成“平均每餐人次”。
- 证据：开发库 14 天返回 1,765，按每餐计算为 617.75。
- 状态：✅ 已改。产品口径确定为“供餐人次 = 当天三餐人数总和”，看板标签已改为“供餐人次”；后端继续返回窗口内的日均三餐合计值。

#### P0-2 公开大屏餐次/全天混合

- 位置：`public/repository.py:24-35`、`public/service.py:60-79`
- 现象：午餐菜品配全天人次和全天投料。
- 状态：✅ 已改。采用分餐次屏口径：公开大屏可切换早餐、午餐、晚餐；`DailyLog.meal_type` 与食物种类均按当前展示餐次过滤；无菜单时不再回退到同日其他餐次。

### P1 · 会造成静默失真或历史不可复核

#### P1-1 油盐糖缺失被写成 0

- 位置：`collection/schemas.py:85-88`、前端 `sheet.ts` 的 `buildSavePayload`
- 建议：字段改为可空；未测量存 `NULL`，显式 0 才存 0；校验层区分“缺测”和“零投放”。

#### P1-2 配方变更重写历史营养

- 位置：`dish/service.py:286-327`、`nutrition/service.py:177-190`
- 建议：引入不可变 `recipe_versions`，历史 `dish_nutritions` 绑定版本；修改配方后只重算明确的未来或指定版本，不默认改写过去。

#### P1-3 第二层校准的样本窗口与历史配方

- 位置：`nutrition/service.py:309-310`、`nutrition/repository.py:212-263`
- 建议：拟合窗口改为 `end = on_date - 1`，当天只做校验；拟合时使用每次采集对应的历史配方版本；明确是否排除 `CALIBRATION_RESIDUAL` 日。

#### P1-4 单菜预测的假日双重折减

- 位置：`forecast/service.py:211-293`、`forecast/repository.py:51-96`
- 建议：单菜历史装载与人数预测使用同一假日过滤规则；工作日/假日 profile 分别构建；补一条“历史含假日、目标为普通日/假日”的回归测试。

#### P1-5 三餐各自的每日油盐糖上限

- 位置：`targets.py:102-123`、`menuplan/service.py:300-360`
- 建议：如果目标是全天合规，增加餐次分配或三餐汇总硬约束；如果保留现有设计，必须在推荐结果和验收文档中明确“每餐各自用日上限，不能证明全天合规”。当前文档已提示，但产品仍可能误读。

#### P1-6 证据优先级没有时效

- 位置：`nutrition/service.py:579-625`
- 建议：给抽样/校准设置有效期或降权策略；至少让用户看到“这个 SAMPLED 值来自多少天前”。

#### P1-7 抽样修正跨餐次

- 位置：`nutrition/repository.py:438-470`
- 建议：明确是全局烹饪方式修正还是同餐次修正；如果是后者，查询加 `meal_type` 条件并补测试。

#### P1-8 数据库约束没有文档说得那么强

- 位置：`data-model.md:164-177`；实际 `ingredients`、`seasonings`、`dishes`、`recipe_items`、`recipe_seasonings` 无营养/价格/用量 CHECK。
- 建议：既然 API 层已用 Pydantic 校验，至少修正文档；若要把数据库当最后防线，应补 `edible_ratio BETWEEN 0 AND 1`、价格/用量/份量非负、正数等约束。

#### P1-9 0 人次 API 边界

- 位置：`collection/schemas.py:85` 允许 0；`nutrition/engine.py:576-590` 要求大于 0。
- 建议：保存采集时在 service 层拒绝 0 人次并返回 `422/400` 结构化错误，或允许保存但不生成人均结果并明确标记“不可计算”。

### P2 · 数据治理与可维护性

1. 食材/调味料价格没有来源和报价日期，当前全部是演示值；生产接入前应新增价格来源模型。
2. 蚝油在新旧数据库中的营养值可能不同（旧值保留、新值 NULL），种子不具备严格收敛性。
3. Excel 导入允许调味料来源为空，且没有 `source_version` 列，实际上绕过了“营养必须可追溯”的约束。
4. 当前开发库有测试残留：active dish 26 而非种子的 25；旧测试食材/调味料 inactive 但未清除。
5. `feedbacks` 表没有任何业务写入，属于未完成扩展表。
6. 浪费率在产出重量为 0、剩餐大于 0 时返回 0，可能掩盖异常数据；剩餐重量也没有与出餐重量/剩余比例做交叉校验。
7. `forecast/models.py:46` 的日历注释、`data-model.md` 的表数量均过期。
8. `EXCLUDED_FLAGS` 与 `is_anomalous` 没有被实际调用，容易让维护者误以为只有清单中的异常才排除。

## 7. 建议的修复顺序

1. **先修两个 P0 展示口径**：看板人次、公开大屏餐次/全天口径；这是用户最先看到、也最容易造成误解的数字。
2. **把采集输入改成“可缺失”**：油盐糖 `NULL`、显式 0、缺失提示，修 0 人次 API 边界。
3. **建立不可变配方版本**：历史营养不再被新配方回写；补版本切换的回归用例。
4. **重做第二层校准的样本边界**：目标日排除、历史配方版本、异常日规则。
5. **统一单菜预测与人数预测的假日过滤**；补带假日历史的测试。
6. **决定三餐油盐糖是“每餐分别上限”还是“全天合计上限”**，并在求解器、页面、验收标准三处统一。
7. **补价格来源/报价日期**，把演示价格从生产配置中隔离出去。
8. **收口文档与测试**：表数量、日历注释、DB CHECK、遗留表和死代码。
