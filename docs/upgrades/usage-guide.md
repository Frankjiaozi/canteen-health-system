# 知味：五分钟使用流程与下一步

用于介绍已经实现的能力，不把未来规划或合成数据讲成已落地成果。

## 开始前

从系统菜单打开 Docker，确认开发数据库运行；仓库根目录运行 `pnpm dev:demo`。打开 <http://127.0.0.1:5173/admin/agent>，用示例录入员 `recorder / canteen@2026` 登录。不要在原有台账执行 `db:seed` 或 `db:reset` 来准备功能验证。

现在没有真实模型密钥，界面显示“规则模式”。如需介绍模型 Agent，应先按 Ethan 指南配置支持工具调用的模型并完成真实验收；否则明确说明本次功能验证的是可运行的业务工具链与有限任务识别。

## 使用流程

| 时间 | 操作 | 观众应看到的重点 |
| --- | --- | --- |
| 0:00–0:30 | 简介、展示数据说明，点“先检查数据” | 知味面向食堂人员；检查候选、配方、单价和本餐次历史，当前为合成示例 |
| 0:30–1:20 | 新建任务，发“明天午餐800人，预算少一点，安排菜单与采购”，再回答“7元” | 先澄清、保留已明确人数；实际查菜、体检、计算，得到草案，尚未发布 |
| 1:20–2:00 | 发“改成1000人，每人预算9元，其余条件不变” | 条件与采购随之更新，保留上一版，比较人数和金额差异 |
| 2:00–2:40 | 点一道菜的“换菜” | 明确排除此菜，重算整餐；结果可能调整不止一道菜，解释保持一致 |
| 2:40–3:30 | 打开营养、采购、计算依据 | 有差距就显示差距；成本、份数与原始假设可追溯，不能把所有结果都说成达标 |
| 3:30–4:10 | 预览完整报告、下载采购 CSV，核对后确认发布 | 报告带版本、来源与风险；确认人和时间可见，实际菜单更新。发布没有代替实际采集，也没有向供应商下单 |
| 4:10–4:40 | 发“核查最近7天供应记录” | 检查真实接口返回的示例记录。可能是零问题，这也是有效结果；异常原因需要人工核查 |
| 4:40–5:00 | 展示手机结果/条件切换和历史任务 | 手机可用、刷新可恢复，两人按接口独立开发 |

采购金额由当时的数据和约束决定，不背固定数值。不同日期、人数、菜库或前一天菜单都可能改变结果。发布若提示配方/价格/菜单变化，应展示重新生成流程，不绕过校验。

## 当前可以说明的特色

1. **对话后能执行完整业务流程。** 计算有业务工具，结果有版本，正式写入有独立人工确认。
2. **可以核对与纠正。** 保留方案、比较约束和金额、定位采集记录、说明数据不足与计算假设。
3. **两人可以独立推进。** Agent、前端、业务服务分离，统一契约，业务服务无需模型也能运行。
4. **数据不足有明确出口。** 没有某餐次历史时显示阻塞与原数据入口，不借其他餐次拼结果；歧义未解决时，模型发来生成参数也不能替代用户的回答。

## 20 日前建议优先完成

| 优先级 | Ethan：前端与 Agent | 协作者：业务与数据 |
| --- | --- | --- |
| 首要 | 配置真实模型，验证多轮保留条件、换菜、无解、模型中断；修复真实反馈 | 核对配方/单价/份数策略与营养目标，提供缺失项和来源，不编造食堂记录 |
| 其次 | 用手机和初始化账号走一遍；按实际效果录屏并统一解说 | 扩充有来源的菜品/配方或标明合成；完善历史不足和无解说明 |
| 最后 | 整理作品介绍、功能证据、操作视频和材料，逐项对照比赛指南 | 固定可复现的环境与数据版本，确认部署和数据备份方式 |

时间不足时暂缓完整 RAG、个人膳食、库存/过敏原、自动下单与多租户。比赛材料中的创新、效果与完成程度必须以实际实现和验证为依据；本文件不替代官方比赛提交要求。
