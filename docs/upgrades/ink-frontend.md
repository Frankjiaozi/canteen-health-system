## 业务衔接审查（2026-10-20）

范围：导航与路由、三类账号、菜单生成/同步/撤回、采集与离线队列、看板统计、菜品图片、登录注册及公开大屏。后端仅阅读、运行既有测试和无数据库写入的诊断；本轮没有修改后端业务规则。以下区分修复、确认的问题与尚未实现的能力，不代表完成全量安全审计。

### 已修复的前端问题

1. **导航切换后目录变化。** 首页与内页原先使用两套菜单和 178/218px 两种宽度。现在共享同一菜单、固定宽度与侧栏样式，选择由路由决定；展开状态保留，直接访问子页/浏览器后退会展开所在分组。
2. **离线队列跨账号和重复提交风险。** 队列增加账号归属，同日同餐不同账号不会覆盖；列表、数量、自动/手动补交均按当前账号过滤，学校账号不能补交。自动和手动补交共用执行锁，失败条目不再因状态更新无限重试；账号变化暂停余下条目；旧请求完成不会删除更新后的草稿。
3. **旧版无归属队列。** 保留本地原始内容，暂停自动补交并提示核对后重新录入，不推测属于当前用户。头像仍仅本浏览器保存，没有增加服务端头像接口。
4. **菜单条件与结果错位。** 方案的日期/餐次必须匹配当前选择才能显示和同步；批量模式换餐次时清空上次结果。生成/导入期间禁用条件切换及冲突操作，三餐同步和批量导入增加日期确认。
5. **重存采集单清空逐菜重量。** 原先构造请求时把每道菜的 `leftover_weight_g` 固定写成 `null`；现在保留接口已有值。没有据此擅自改变后端浪费率算法。
6. **变更后显示旧数据。** 采集保存、离线补交、校准及 Agent 发布/撤回补充相关查询缓存失效。只影响本页面 QueryClient；另一个公开大屏浏览器仍按原有五分钟轮询刷新，并非实时推送。
7. **只读页面文案承诺不实。** 菜单页原先声称其他账号生成后学校账号就能在此看到结果，但结果实际只存在生成者页面的 mutation 状态。改为引导查看已发布菜单与供餐记录，完整采购历史仍未接入。

### 后端已确认的问题，暂未修改

| 优先级 | 触发与影响 | 代码证据/建议 |
| --- | --- | --- |
| 高 | 采集页提交整餐剩餐总重，但看板读取逐菜重量之和，采集列表和看板会展示不同浪费率。未填逐菜重量又被折算成 0，容易误报“零浪费”。 | `analytics/repository.py:load_waste_rows` 对比 `collection/service.py:list_logs`；`analytics/service.py:build_waste` 把 None 转 0。需确定统一的整餐/逐菜优先口径，保留缺测状态。 |
| 高 | 历史已供应菜品停用后，再打开采集单会遗漏该菜。重新整份保存可能删除历史明细。 | `collection/service.py:build_sheet` 只遍历 `load_active_dishes`，保存时整份 `replace_items`。应将历史已记录/已安排菜品并入读取结果，停用只限制新增选择。 |
| 高 | 批量导入按日期查“最新方案”，没有绑定用户刚核对的方案 ID。另一用户在核对后重新生成，最终可能导入另一版。 | `menuplan/service.py:sync_batch` 调用 `latest_suggestion_id`；单个方案的快照/目录/菜单并发检查已存在，但并不能绑定批量界面上看过的版本。需让批量请求带逐日方案 ID/版本。 |
| 中 | 无可比较指标时合规率返回 0%；无有效分母时部分人均指标返回 0，混淆未知与真实零。 | `analytics/service.py:_ratio`、`_str_or_zero`。前端能补缺日期，无法可靠还原已经被接口变成零的缺测信息；建议接口返回 nullable 数值。 |

只读诊断复现：

- 对 `build_waste` 输入“出品 1000g、剩餐重量缺失”，返回 `leftover_weight_g='0'`、`waste_ratio='0.0000'`。
- `_ratio(0, 0)` 返回 `'0.0000'`，`_str_or_zero(None)` 返回 `'0.00'`。
- 模拟菜单含已停用菜品、在用菜库为空，`build_sheet` 返回 `menu_confirmed=True` 但 `dishes=[]`。
- 以上是独立 mock 输入的服务函数诊断，不对真实台账做修改。

## 审查后的修复（2026-10-20）

用户在上述问题汇报后要求继续处理。本节为最新状态，覆盖前文“暂未修改”和“仍需补齐”中的对应项。修复涉及前端及已确认的后端缺陷，保留原有三类账号权限、推荐/预测算法和发布/撤回校验，不需要数据库迁移。

1. **统一浪费率口径。** 看板按采集单的整餐剩餐总重计算，先按餐聚合出品重量，避免多道菜重复累计整餐总重；任一已记录餐次缺少剩餐重量，当天按缺测展示。真实零仍为零。
2. **保留未知指标。** 合规率无可比较项目、浪费率无有效出品重量、人均指标无有效人次时返回 `null`，不再冒充 0；均值排除缺测值。客户端类型同步更新。
3. **保留历史停用菜品。** 采集单包含当天已安排及已记录的菜品，停用后仍可读取并原样保存历史明细；无历史关联的新日期仍只列在用菜品。
4. **批量导入绑定已核对版本。** 前端提交逐日 `suggestion_ids`，后端只导入指定版本，继续执行原有日期、餐次、快照与并发校验。没有指定方案的日期跳过，不再自动选取最新方案。
5. **菜单与采购历史。** 新增只读历史接口和页面入口，从已保存的完整快照恢复菜品、份数、采购量与金额，学校账号也可查看。按日期最多读取最近 100 条推荐记录中的完整方案；更早且没有完整快照的记录不会被重新推算成历史数据。
6. **未保存提示。** 采集单编辑后，切换页面、日期或餐次会先确认；关闭/刷新页面触发浏览器离开提醒。保存期间锁定输入，保存成功解除提醒。
7. **注册开关联动。** 前端读取服务端已有注册开关；关闭时隐藏注册入口，直接访问注册页也不显示提交表单，提示联系管理员。未新增账号邀请流程或扩大角色权限。

接口兼容性：批量导入现在必须携带方案 ID 请求体，旧调用缺失时返回 422；统计字段新增空值语义。发布时需要前后端同步更新。跨设备大屏仍按原有轮询刷新；头像仍保存在本浏览器。

验证：业务 API 全套 344 项、Agent 103 项、前端 128 项单测通过；20 项浏览器回归覆盖登录/退出、账号/头像、侧栏一致性、菜单条件切换、关闭注册、未保存提示和只读历史恢复。API 测试使用独立 `canteen_upgrade_test`；浏览器新增历史数据使用拦截响应，不向演示台账导入测试数据。Ruff、mypy、ESLint、TypeScript 与生产构建通过。构建保留已有的大体积 chunk 提示，测试环境保留第三方弃用提示。
