# Ethan：前端、视觉与 Agent 开发指南

本指南对应 2026-10-16 两轮升级。业务边界与字段统一见 [共同契约](shared-contract.md)，业务协作者可独立阅读 [后端指南](partner-backend-data.md)。

## 这条线负责什么

你负责用户能看到、能操作的整条路径：进场动画、导航与手机适配、膳食助手、任务条件、执行过程、方案比较、人工确认、采购导出，以及模型适配与工具编排。协作者负责计算和真实执行。

首版任务：安排一餐菜单与采购；改人数或每人预算；按完整菜名排除菜品并重算；解释方案；核查最近若干天记录；人工确认最新方案并写入正式菜单。最终数字来自业务服务。

工程分成独立进程，不把 Agent 代码塞进页面：

```text
apps/web/src/features/agent/
  AgentPage.tsx                   对话与结果的页面协调
  api/client.ts                  唯一 Agent 请求与 NDJSON 解析入口
  api/schema.d.ts                Agent OpenAPI 自动生成，不能手改
  api/types.ts                   复用生成类型与业务结果类型
  components/TaskPanel.tsx        日期、人数、预算、排除条件、历史任务
  components/ConversationView.tsx 消息、实际步骤、输入框
  components/ResultPanel.tsx      菜单/营养、采购、对比、依据、确认
  lib/compare.ts                 仅做展示差异，不做业务计算
  agent.css                      工作区视觉与响应式样式
apps/agent/zhiwei_agent/
  config.py                      独立环境变量
  main.py                        登录态校验、会话路由、发布入口、导出
  business.py                    业务 HTTP 客户端，唯一调用边界
  schemas.py                     Agent 输入输出模型
  store.py                       独立 SQLite，按当前账号保存
  runner.py                      受限工具循环与逐步事件
  tools.py                       六个受限工具白名单，生成前强制体检
  rules.py                       明确标注的规则模式
  model.py                       Chat Completions 模型适配
  exports.py                     CSV 与 Markdown 核查报告
  report.py                      版本快照的自包含 HTML 完整报告
```

进场动画在 `features/intro` 与 `public/intro`。本次保留左到右渐进显墨、宣纸与大块动态背景、全宽弯曲墨迹进度和透明红印章；没有右下角播放控件。后续 Agent 改动不要重新设计已确认的动画。

## 先运行，再改功能

前置：Node、pnpm、Python 3.13、本机 PostgreSQL（项目默认 Docker 开发库）。Docker 请从系统菜单启动，避免当前 Windows/Codex 直接启动 Docker 的已知环境问题；本脚本不会自动开 Docker 或恢复出厂。

首次安装依赖后，在仓库根目录：

```powershell
pnpm install --frozen-lockfile
uv pip install --python apps/api/.venv/Scripts/python.exe -e "apps/api[dev]" -e "apps/agent[dev]"
pnpm db:up
pnpm dev:demo
```

如果没有现成虚拟环境，先 `python -m venv apps/api/.venv`。没有 uv 时可使用该解释器的 pip 安装同样两份依赖。

`dev:demo` 创建/使用独立 `canteen_agent_demo`，只在空库初始化示例数据；不会重写原 `canteen`。业务服务 8002、Agent 8001、前端 5173。页面明确标注合成数据。演示账号 `recorder / canteen / school`，口令 `canteen@2026`；这些是示例账号，不能用于真实对外部署。

连接现有开发数据用 `pnpm dev`：业务服务 8000、Agent 8001、前端 5173。启动前检查数据库与迁移，端口占用会说明原因，不自动杀其他进程。默认 Python 服务稳定启动，修改 Python 后重启；前端仍热更新。确需 Python 自动重载可用 `node scripts/dev-stack.mjs --watch`（演示另加 `--demo`）。当前 Windows 会话中重载曾中断服务，演示建议默认启动。

两人分别开发时可以只运行 `pnpm dev:api`、`pnpm dev:agent`、`pnpm dev:web`。本机可共用开发解释器；发布时 Agent 与业务服务使用各自镜像、各自依赖。

## 无密钥也能演示，但必须说明模式

`apps/agent/.env.example` 复制为同目录 `.env`。三项都填好后，`auto` 才启用模型：

```dotenv
AGENT_MODEL_BASE_URL=https://你的服务地址/v1
AGENT_MODEL_NAME=供应商支持工具调用的模型名
AGENT_MODEL_API_KEY=仅填本机环境文件
```

接口地址应指向 Chat Completions 的基址，代码会追加 `/chat/completions`。生产必须 HTTPS，本机调试仅允许 localhost/127.0.0.1 的 HTTP。不要把密钥放进前端、Git、日志或截图。

- `rules`：只识别有限任务，仍调用真实业务工具，不伪装大模型。
- `auto`：配置完整用模型，否则规则模式，界面显示实际模式。
- `model`：缺少配置就启动失败，避免静默假装连接成功。

产品不绑定 DeepSeek。协作者用 DeepSeek 写代码与这里的模型设置是两件事。兼容层依据 [DeepSeek 官方工具调用说明](https://api-docs.deepseek.com/guides/tool_calls/) 的标准函数调用往返形式实现，也可连接兼容协议的其他服务；不保证任意供应商或推理模式都完全兼容。首版不发送/展示隐藏推理。

目前没有配置真实模型密钥。已实现适配层和模拟模型协议测试；真实供应商、网络、工具能力与实际回答质量需要配置后另做验收。

## 用户流程与页面状态

1. 面板选日期和餐次。人次留空则用目标日期之前同餐次最近采集；每人预算默认 8 元，这个值在面板明确可见。可先“检查数据”，查看缺项和原数据入口。
2. 发任务或点击“安排菜单与采购”。执行区只显示实际发出的查询/计算步骤。
3. 生成后恢复真正使用的条件，结果区显示版本、采购合计、营养差距与警告。
4. 改人数/预算或点击具体菜的“换菜”，重算形成新版本，旧版本保留。
5. “方案对比”看增加/移除菜品和采购差额。日期/餐次不同会提示不能直接比较优劣，人数不同也不能把差额叫做节省。
6. 只能确认当前最新版本。确认弹窗列日期、餐次、人数、菜品和风险；HTTP 发布成功后才显示“已确认发布”。
7. 导出按所选版本生成，草案也标明待确认，不向任何供应商发送。
8. “预览报告 / 下载完整报告”包含条件、菜单、采购、差距、依据与当时体检；HTML 离线可用、可打印成 PDF，没有服务端原生 PDF 导出。“载入此版条件”只填参数并提示重新计算。

必须保留的状态：服务未启动、登录过期、只读角色、历史不足、求解无解、缺单价、营养不达目标、版本冲突、配方或价格变化、模型失败、网络断流。错误时保留已完成结果。服务临时断开时认证页提供“重新连接”，不让用户误以为口令错误。

规则模式示例：

```text
明天午餐800人，每人预算8元，安排菜单与采购
改成1000人，预算每人9元，其余条件不变
换掉番茄炒蛋，其余条件不变
清空排除，重新安排菜单
解释当前方案
核查最近7天供应记录
按当前条件做数据体检
明天午餐1000人，预算少一点，安排菜单
7元
```

规则模式要求数字与完整菜名。含糊、范围或矛盾条件先给补充问题；已明确的日期、人数等会保留。多项待答时逐项解决，部分回答和无关解释不能清空其他问题。可直接回复数值、点击候选回复，或“取消补充”；历史候选按钮停用。特殊膳食、库存等不支持的条件不能默默忽略。

## 模型和工具的约束

只开放共同契约中的六个工具。模型可以理解、澄清、查询、检查数据、调用生成、解释；没有发布权限。发布按钮直接走受限服务端路由，以当前用户身份调用业务确认，不经模型。

同会话任务串行；一请求最多生成一份；最多 5 轮模型调用，总超时 180 秒。Pydantic 校验工具参数，拒绝未知工具。Cookie 只送业务服务，不送模型；对话库不保存 Cookie 或密钥。

会话保存至 `apps/agent/data/*.sqlite3`；原始业务数据仍在 PostgreSQL。每会话最多 200 条消息、40 版方案，达到上限新建任务。首版是单实例 SQLite 方案，适合本次演示；没有跨设备实时协作、会话分享、长任务后台队列或完整 RAG 知识库。

## 视觉与交互规范

- 纸白与浅绿承接知味水墨身份，墨绿强调行动；朱红仅用于风险。
- 桌面任务条件、对话、结果分区；手机用“对话 / 结果 / 条件”切换，导航使用抽屉，所有表格限制在自身容器滚动。
- 不堆动效；加载和工具状态是行为反馈。文字和数字比装饰优先。
- 不把工程细节放到业务流程里；模式、来源与计算假设会影响决策，需要可见。
- 保留键盘焦点、输入标签、中文输入法 Enter 保护、减弱动态效果设置。
- 对话滚动只移动对话区，不能把整页标题和操作区突然推走。

## 和业务协作者如何并行

你只对共同契约提出业务能力，不让同伴照截图猜 JSON。他改业务模型/接口后自己生成业务类型并提供样例，你负责 Agent 消费与页面呈现。你改 Agent 协议自己生成 Agent 类型，不让他动页面组件。

共享启动、nginx、Compose、全局主题和路由由你汇总。协作者提交数据库迁移时，你配套升级演示与测试环境。不要一起改同一份锁文件或生成物。

推荐后续顺序：先用真实模型验收多轮改条件与工具错误恢复；再完善移动端实际使用细节和演示脚本；最后考虑知识检索、报表 PDF、更多约束。新增过敏原、偏好或个人膳食能力前，需要业务数据和用户需求，不能靠提示词声称支持。
