# 数据模型

共 17 张表。表的定义分散在各业务域的 `models.py` 中，由 `app/db/registry.py` 统一注册，
Alembic 只依据该注册表生成迁移。

## 一、三条全局约定

| 约定 | 做法 | 原因 |
| --- | --- | --- |
| 主键 | 全部使用 UUID，由**应用层**生成 | 重复提交（重试、误点两次、脚本重放）天然幂等，不需要额外的去重逻辑 |
| 时间 | 业务日期用 `DATE`，时间戳用 `timestamptz` | 食堂按「哪一天」组织数据，不能受服务器时区影响 |
| 枚举 | `VARCHAR(32)` + `CHECK` 约束 | PostgreSQL 原生 `ENUM` 每改一个取值都要 `ALTER TYPE`，迁移与回滚代价过高 |

枚举的取值以**稳定的英文大写常量**存储，中文展示名由 `app/shared/enums.py` 的
`ENUM_LABELS` 统一维护。改文案不需要动数据。

枚举列一律通过 `enum_check()` 显式声明唯一的一条 CHECK 约束——若打开 SQLAlchemy 的
`Enum(create_constraint=True)`，表级与 metadata 级会各注册一条，迁移里会出现重复约束。

## 二、表清单

### 认证与留痕

| 表 | 说明 |
| --- | --- |
| `users` | 账号。仅三类可登录角色：食堂录入员、食堂管理员、学校管理方。**系统内没有学生账号** |
| `audit_logs` | 操作留痕，只增不改。除 `actor_id` 外另存冗余的 `actor_name`，账号被停用后历史留痕仍可读 |

### 食材与调味料

| 表 | 说明 |
| --- | --- |
| `ingredients` | 食材库，营养成分以**每 100 克可食部**计 |
| `seasonings` | 油盐糖等调味料，单独建表：既是营养计算的关键变量，也是每日采集的对象 |

`ingredients` 与 `seasonings` 的五项营养指标**可空**。食物成分表里部分条目确实缺项，
把缺失写成 0 会让营养核算静默失真；计算引擎遇到空值时会记入可追溯快照并放宽误差区间。

### 菜品与配方

| 表 | 说明 |
| --- | --- |
| `dishes` | 菜品。含类别、烹饪方式、标准份量、单锅份数、过敏原、配方版本 |
| `recipe_items` | 配方中的食材用量。唯一键 `(dish_id, ingredient_id)` |
| `recipe_seasonings` | 配方中分摊到单份的调味料用量。单独建表，因为它在校准模型中承担「锚点」角色 |

配方用量单位统一为克（列名带 `_g` 后缀），避免出现无法参与计算的单位。
删除菜品时配方明细级联删除；被配方引用过的食材不允许物理删除。

### 菜单

| 表 | 说明 |
| --- | --- |
| `menu_days` | 某天某一餐的菜单。唯一键 `(date, meal_type)` |
| `menu_day_items` | 菜单日里的一道菜，含计划份数与「临时替换」标记 |

`is_substituted` 用于标记实际供应与计划不一致的情况，避免这类日子污染预测的历史序列。

### 每日采集与反馈

| 表 | 说明 |
| --- | --- |
| `daily_logs` | 每日记录主表，唯一键 `(date, meal_type)`。含就餐人次、油盐糖总用量、剩餐总重、异常标记 |
| `daily_log_items` | 出品明细：每道菜的出餐份数与剩余比例 |
| `feedbacks` | 剩餐与评分反馈，由录入员代录 |

`anomaly_flags` 里的标记有两个来源，界面上必须分开呈现：

- 录入员勾选的「临时接待 / 菜品停供 / 设备故障」——提交时以本次表单为准；
- 系统回写的「用量对不上」——校准算完发现当天总量与拟合预测偏差过大时写入，
  录入员把用量改对、重跑校准后自动撤掉。

两者不能互相覆盖：重新保存采集单时人工标记以表单为准，系统标记原样保留。
这些日子的数据**不进预测的历史序列**——异常份数进了移动平均会把预测带偏。

### 营养结果

| 表 | 说明 |
| --- | --- |
| `dish_nutritions` | 菜品营养结果，含误差区间与可追溯快照 |
| `calibration_factors` | 校准系数。系数**按类别分开存**（`coefficients` JSONB，第二层是油 / 盐 / 糖各一项，第三层是 `OVERALL` 整体系数）；`dish_id` 为空表示这条系数针对整类烹饪方式 |
| `nutrition_standards` | 膳食指南量化基准，配置化存储并带来源与原文引用 |

`calibration_factors` 不设唯一约束，替换语义由 service 负责：同一 (日期, 餐次, 烹饪方式, 来源,
菜品) 只保留一行。抽样那天可能测了同一烹饪方式的几道菜，各带自己的 `dish_id`，唯一约束反而会卡住
这种正当用法。查询用索引 `(date, meal_type, cooking_method, source)`。

系数不合成一个数字，是因为油、盐、糖的偏差幅度本来就不一样（多放油很常见，多放糖不常见），
合成需要一个加权方式，而任何一种加权都没有客观依据。

### 预测与推荐

| 表 | 说明 |
| --- | --- |
| `forecasts` | 份数预测，含置信区间、模型版本与输入特征快照 |
| `menu_suggestions` | 菜单推荐，含候选菜单、营养差距、成本估计与推荐理由 |
| `holidays` | 法定节假日日历，含「放假 / 调休上班」两种类型与是否已核对 |

`holidays` 单独立表而不是写死常量，是因为**调休年年不同、且必须以国务院办公厅通知为准**。
2026 年的日历（33 天放假 + 6 天调休上班）逐条取自国办发明电〔2025〕7 号，由数据迁移写入，
因此任何环境跑完迁移就有一份完整且已核对的日历，不依赖演示种子脚本。
`is_verified` 记录核对状态，界面上仍有核对入口供后续年份与调整使用。

放假与调休在预测里的处理**不同**：放假日是整体下调（人还在校的那部分少了），
调休上班日则是**换一套基线**——调休那天多半落在周末，而周末的基线本身就不适用，
拿其它周日的历史去估会低一大截。这一条写在 `forecast/strategy.py` 的 `DayContext` 里。

## 三、口径分离（本系统最容易出错的地方）

`dish_nutritions` 用两个**互相独立**的维度标记每个数值，禁止混用：

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| `caliber` | `PER_SERVING` | 一份菜的营养，服务公开大屏与菜品查询 |
| | `PER_CAPITA` | 这道菜分摊到每位就餐者的摄入量，服务看板与政策对标 |
| `value_type` | `THEORETICAL` | 按标准配方推算 |
| | `CALIBRATED` | 用当日油盐糖实际用量做闭环校准后的值 |
| | `SAMPLED` | 抽样称重实测值 |

`PER_CAPITA` 的定义是该菜**实际被吃掉**的营养 ÷ 就餐人次；把当日全部菜品的该口径相加，
即为当日人均摄入。单份与人均混用会得出完全错误的结论，这是同类系统最常见的错误。

三份数值并存不覆盖，所以每个读取方都要回答「取哪一份」。这个判断统一收在
`app/shared/nutrition_values.py`：**抽样实测 > 当日校准 > 配方理论**。公开大屏与管理端看板
都走这一处，避免两个界面对同一道菜给出不同的数字。看板按天汇总人均摄入时，必须先按
「菜品 + 餐次」各取一份再相加——三份全加等于把同一道菜算三遍。

## 四、可追溯

任何营养数值都要能回答「这个数是怎么来的」，因此：

- `dish_nutritions.computation_trace` 保存配方快照、食材成分来源、所用校准系数、公式版本，
  以及计算时缺失的数据项。
- `dish_nutritions.uncertainty` 逐项保存误差区间。系统给区间而不是看似精确的点值。
- 食材营养数据逐条记录 `data_source` 与 `source_version`。
- 配方与菜单的修改通过 `audit_logs` 记录操作人、时间与前后值。
- 菜品列表里，**从未被排进过菜单**的菜品显示的是按当前配方现算的预览：接口里 `date`
  为空即表示它不属于任何一天，也**不写入 `dish_nutritions`**。它只服务「录完配方立刻
  核对数值」这一件事，公开大屏、看板与报表读的始终是落库结果。

## 五、约束策略

除枚举取值约束外，数据库层还挡这些情况：

- 计数与用量不得为负（`diner_count`、`servings_produced`、各项营养值等）。
- 比例必须落在 0~1（`leftover_ratio`）。
- 评分必须在 1~5。
- 置信区间与目标区间必须有序（`ci_lower <= ci_upper`）。
- 膳食指南基准至少要有一个边界（只有上限、只有下限或上下限都有）。

代码里绕过枚举或业务规则直接写库，会被数据库拒绝——这是「不静默失败」的最后一道防线。
