# 架构说明

## 一、总体形态

单仓多包（pnpm workspace）+ 前后端分离 + **两个后端进程**：业务的模块化单体，加一个独立的 Agent 服务。

```
浏览器
  │
  ▼
web（nginx，宿主机 :8080 → 容器 :80）
  ├── /              SPA，找不到的路径回 index.html
  ├── /api/          → api:8000
  └── /agent-api/    → agent:8001
        │
        ├──► api —— FastAPI 模块化单体（:8000，启动时先 alembic upgrade head）
        │        │
        │        ▼
        │    postgres（:5432）
        │
        └──► agent —— FastAPI（:8001）
                 ├── 自己的 SQLite：对话、方案版本、报告快照
                 └── 用**浏览器带来的 Cookie** 调 /api/v1（唯一的业务出口）
```

只有前端端口对外（默认 8080），api、agent、postgres 都在容器网络内部，外面连不到。
前端与后端同源部署，因此登录凭证用 httpOnly Cookie 传递，前端代码不接触 token——
同源才走得通，也就不需要为跨域凭证另做配置。

### 为什么 Agent 要单独一个进程

不做成 api 里的又一个模块，有三条实在的理由：

1. **依赖面不同**：它要模型客户端和自己的 SQLite，与业务服务的发布节奏无关；
2. **故障要隔离**：模型超时、限轮次、供应商抽风都只影响它自己，业务接口照常可用；
3. **权限边界落在进程边界上**：它**没有业务库的写权限**，只能拿当前用户的身份走 HTTP。
   于是「AI 不能自己拍板」不靠提示词自觉，而是靠它根本没有那条路。

### 只有一个助手：知味膳食助手

系统里**只有一个 AI 入口**，就是独立进程里的「知味膳食助手」。业务侧原先还有一个
「AI 助手」抽屉（能改食材、菜品、菜单，带确认卡与撤回），已经整套下线——
两个入口做同一批事、各记各的对话、各配一个模型，用户只会问「我该找哪个」。

它负责这一条线：**数据体检 → 生成方案 → 改条件重算 → 版本对比 → 人工发布 → 撤回**。
边界写死在进程上：

| 能力 | 是不是模型能做的 |
| --- | --- |
| 查询、体检、生成、解释、改条件重算 | 是，走固定的受限工具白名单 |
| **发布 / 撤回** | **不是**。页面点按钮，走独立路由以本人身份调业务接口 |
| 改食材、改菜品配方、录采集 | 不开放写操作。这些在各自的页面上做；助手只做查询与菜单方案 |

**撤回不是助手私有的**：它落在 `POST /api/v1/menu-plan/{id}/undo` 上，助手只是调用方。
以后要给别的界面加撤回，不用再经过这个助手。

### 三种跑法

| 命令 | 业务 API | Agent | 前端 | 数据库 | 用在哪 |
| --- | --- | --- | --- | --- | --- |
| `pnpm docker:up` | 容器内 :8000 | 容器内 :8001 | **:8080** | 容器卷 `canteen-pg` | 演示与内网部署 |
| `pnpm dev` | :8000（热重载） | :8001 | :5173（热更新） | 开发库 `canteen`（:5432） | 平时改代码 |
| `pnpm dev:demo` | **:8002** | :8001 | :5173 | **`canteen_agent_demo`**（独立库） | 给人演示，不碰你的数据 |

`pnpm dev` 不是一行 `concurrently`，而是 `scripts/dev-stack.mjs`，按顺序做三件事：

1. 检查 8000 / 8001 / 5173 有没有被占——占了就说明原因并退出，**不会去杀别人的进程**；
2. 跑 `app.preflight`：连数据库、比对 alembic 是否到 head、确认 Agent 依赖装没装；
3. 拉起三个进程，任何一个挂掉就把整组停掉。

### 数据存在哪

| 数据 | 位置 |
| --- | --- |
| 食材、菜品、配方、菜单、采集、营养结果、预测、推荐、用户、审计 | PostgreSQL |
| 助手的对话、方案版本、报告快照 | Agent 自己的 SQLite（容器里是 `agent-state` 卷） |
| 测试数据 | `canteen_upgrade_test`（`pnpm test:py` 自动建/用） |
| 演示数据 | `canteen_agent_demo`（`pnpm dev:demo` 自动建/灌） |

测试与演示各用各的库，`canteen` 只留给你手上正在看的那套。

## 二、后端分层

依赖方向严格单向，**不允许反向或跨层引用**：

```
router  →  service  →  repository  →  db
（HTTP）   （业务）     （数据访问）    （引擎/会话）
```

- `app/core/` 配置、安全、通用依赖、领域异常与统一异常处理器、日志。
- `app/db/` 引擎与会话、声明基类与审计 mixin、迁移、种子数据。
- `app/modules/<域>/` 每个业务域固定五件套：
  - `models.py` —— SQLAlchemy ORM 模型
  - `schemas.py` —— Pydantic 请求/响应模型
  - `repository.py` —— 数据访问，只做查询与持久化，不含业务规则
  - `service.py` —— 业务规则与事务边界
  - `router.py` —— HTTP 层，只做参数校验与调用 service

### 跨域协作规则

跨业务域只允许调用对方的 **service**，禁止 import 对方的 `models.py` 或 `repository.py`。
这条规则保证了业务域可以独立演进，也是「模块化单体」相比传统按类型分层最重要的收益。

### 唯一的例外：营养域的跨域读模型装配

`app/modules/nutrition/repository.py` 可以引用其它域的 ORM 模型，这是全项目唯一一处例外。

原因是营养计算天然要横向读取五个域的数据（菜品与配方、食材成分、调味料、菜单日、每日记录），
把它们拼成引擎的输入。为此给每个输入都单独造一层 DTO，只会增加间接层而并不隔离任何真实变化——
计算逻辑与这些字段本来就是天然绑定的。

边界仍然清楚：**只读**。任何写入都走各域自己的 service，营养域不修改别的域的数据。

## 三、算法与 IO 分离

`nutrition/engine.py`、`forecast/strategy.py`、`recommendation/solver.py` 一律写成**纯函数**：
输入是普通 dataclass，输出是结果对象，不接触数据库、不读全局状态。

`forecast/strategy.py` 里有一条值得单独说的设计：**同星期样本不足时退化为
「全期平均 × 星期几规律」**，而不是放弃预测或直接套用全期平均。
轮换菜单里一道菜每四五天才出现一次，严格只认同星期几的话一多半的菜都没有预测；
而直接用全期平均，会在周末高估一倍以上（周末在校人数只有工作日的四成多）。
那个「星期几规律」由所有菜的历史一起估出来——单道菜的样本估不出这种规律，
但它对所有菜同时成立，合起来看就非常清楚。实测这一步把回测 MAPE 从 37% 拉回 7.7%。

### 菜单推荐：两条口径与三条经验

目标是「在硬约束下选菜」，用整数规划（PuLP + 自带 CBC）求解。
写成整数规划而不是启发式，是为了让「满足全部硬约束」这句话**可验证**——
启发式只能靠穷举去碰。**PuLP 锁在 2.x**：4.x 不再自带求解器，`listSolvers` 是空的。

**份数不是营养求解的决策变量。** 推荐按「每人一份标准套餐」计算营养：入选的每道菜
各贡献一个标准份，套餐营养是这些单份营养之和。每道菜实际做多少份由 `forecast` 给出，
只用于采购与出餐计划，不再乘进套餐的人均营养；否则预测多做 1.4 倍会被误解成一个人吃了 1.4 份。

**「群体营养供给落在目标区间」是目标，不是硬约束。** 能量下限与蛋白质上限会互相排斥
（现有配方蛋白供能比约 18%，指南区间 10%~15%），两条都当硬约束就是无解。
现在只有油盐糖上限、预算、道数、不连续重复、烹饪方式比例是硬约束；能量与三大营养素
按「偏差最小」求解，并在差距表里逐项给出「差多少、往哪个方向」。

目标区间有两条口径，混起来会得出荒谬的菜单：

- **能量与三大营养素按餐次占比折算**（早/午/晚各 30% / 40% / 30%，**三项各自可配**）。
  它们是「要给够」的东西。三项分开配而不是「只配午餐、另两餐平分剩下的」：
  后者改午餐比例会连带改掉另外两餐，而且早餐与晚餐永远是同一个数——
  那正是三餐菜单会算出一模一样的直接原因之一。
- **油盐糖取每日上限、不按餐次折算**。需求里写的就是「直接引用每日基准」，
  而且按 40% 折算的话，午餐的食盐上限是 2 克，现有任何五道菜的合计都在 4 克以上——
  一餐折算的口径会让模型必然无解。「一餐不超过全天上限」是全天合规的充分条件，
  从不放松要求；真实差距（按折算应 ≤2 克、实际 4.5 克）在差距分析里如实报出。

三条踩出来的经验：

1. **区间中点也要进目标函数**。只要求「落在区间内」，求解器会一路踩到边界，
   交出一份「刚刚好达标」的菜单；把偏差拉向区间中点，结果才像一餐饭。
2. **成本项的量级会比营养偏差大**。成本是「占预算的比例」（0~1），营养是相对偏差
   （常在 0.05 上下），两者等权时成本会把营养挤到边界上。默认权重成本取 0.3。
3. **要有菜品类别的数量上下限**。少了它，求解器会给出「两道汤 + 三道蛋菜」——
   营养上挑不出毛病，但不是一餐饭。

调用方（service）负责把 ORM 数据装配成 dataclass，再把结果落库。这样做的两个好处：

1. 算法可以脱离数据库单测，验收标准里的「5 道菜偏差不超过 15%」「MAPE 回测」可以直接写成断言。
2. 算法实现可以替换（比如启发式换成整数规划）而不影响业务代码。

### 三餐怎么分开：早餐固定，午晚餐不重样

**早餐不参与选菜。** 菜品上有一个「早餐固定供应」标记（`dishes.is_breakfast_staple`），
勾了的就是每天的早餐：学校早饭本来就是那几样，把它当成「待优化的选择」既不符合现实，
也会和午晚餐用同一套目标算出同一份菜单。早餐那条路用 `solver.fixed_plan`——
给定固定菜品按每道一个标准份直接算供给、成本与贴边约束，**复用求解器同一套折算与取整**
（`_sum_field` / `_binding`），只是不做选择；不共用的话，早餐与午晚餐的差距分析没法并排看。

勾了这个标记的菜**同时从午晚餐的候选池里拿掉**：否则同一道菜会在一天里出现两次，
而那是「三餐算出一样」里最难解释的一种表现。早餐菜固定；实际采购份数仍由 `forecast`
按同星期历史与日历修正给出。

**午晚餐不重样。** 求解器的排除集里除了「前一天同一餐次的菜」，还加上
「同一天另一餐已经排上的菜」。两个来源都要看，缺一个都会漏：

| 来源 | 为什么必须看 |
| --- | --- |
| 菜单日 | 已经同步到当天数据的那一餐 |
| 最近一版推荐 | 已经生成、但还没点「同步至当日数据」的那一版 |

只看菜单日的话，先排午餐再排晚餐时，晚餐并不知道刚排的那一版；
只看推荐的话，菜单被人手工改过之后又会拿到一份过期的组合。每餐只取最近生成的那一版。

**主食除外**：主食池里只有米饭与馒头两道，一天两餐都排除的话候选择不出菜单；
而且食堂中午晚上都上米饭本来就是常态。要的是「菜不重样」，不是「连米饭都不能一样」。

### 明日菜单与采购：套餐营养与采购份数分轨

`menuplan` 是编排层，不自己造数：`POST /api/v1/menu-plan/generate` 一次调用把三步串起来，
返回一份自洽的结果。三者分工写在这里，省得以后翻代码去猜：

| 环节 | 谁做 | 输入 | 输出 |
| --- | --- | --- | --- |
| 做哪几道菜 | `recommendation`（整数规划） | 候选菜、营养目标、菜品标准份 | 一份每人套餐、营养差距、推荐理由 |
| 各做多少份 | `forecast`（同星期移动平均 × 日历修正） | 历史份数、节假日日历 | 每道菜的采购份数与依据 |
| 买多少料 | 用预测份数乘配方 | 配方 | 各食材/调味料公斤数与金额 |

**套餐营养与采购份数不再互相污染。** 推荐不再把预测份数当作营养变量；预测仍逐菜独立，
可以先把所有候选菜的份数预测出来，但只用于采购和出餐，不会改变“一个人这份套餐里有哪些菜”。

**就餐人次也单独预测，不复用最近一条采集。** `GET /api/v1/forecast/diner-count`
按同一餐次取最近 8 周历史，排除异常日与法定假日，取最近 6 个同星期几的**中位数**，
再按放假/调休日历修正；样本不足时才退回最近一次采集并标成参考值。任务条件里的
「预计人次」为空时自动填入这个预测值，仍允许手动覆盖；生成与采购使用同一个人数。
指定人数时，情景份数按「指定人次 ÷ 系统预计人次」缩放，不能用最近一条采集做分母——
拿周日 411 人去缩放周二 922 人的菜单，会把份数直接放大一倍。

预测不出来的菜（8 周内样本不足）如实标注为「按每人一份估算」并回落到基准份数，
接口与页面上都写清楚，不装成预测值。

**成本口径：单价是「元/公斤市品」，不乘可食部。** 买菜是按市品付钱，做菜才按可食部算营养。
早先的实现用可食部重量乘市品单价，把成本算低了（合计低 6.25%，清蒸鲈鱼低 42%）。
口径在 `ingredients.unit_price` 与 `seasonings.unit_price` 的模型注释里写明，
界面上表头也标「元/公斤市品」——这个 bug 的根因就是模型里没写单价是什么口径。

采购单**按公斤报、按金额从大到小排**，没有单价的排最后（算不出金额的项不该占着最该先看的位置）。

**一天三餐一次生成。** 页面的默认模式是「一天三餐」：早餐先按固定组合排出，午餐再选菜，
晚餐读取刚生成的午餐并避开它的非主食菜；三餐各自使用自己的系统预测人次。编排层把三餐的
采购项按食材/调味料名称合并成一张单，金额和公斤数为三餐合计。同步仍按餐次分别执行：
某餐已有实际采集就跳过该餐，其余餐次继续，不拿计划覆盖实际供应。

### 同步至当日数据：计划与实际共用一张菜单日

生成只产出**建议**（落在 `menu_suggestions`，含菜品、差距、理由、评估所用的份数快照）。
要让第二天真的按它走，需要一次显式确认：`POST /api/v1/menu-plan/sync`。
它做三件事，缺一不可——写菜单日（`planned_servings` = 计划份数）、按配方算单份营养、
把这一版记为已采纳。少了算营养这一步，大屏第二天早上还是空的（大屏只展示有营养结果的菜）。

`menu_days` 因此先后扮演两个角色：**采集提交之前是「计划供应」，之后是「实际供应」**。
不新开一张「计划表」，是为了「这一天供应了哪些菜」始终只有一份数据——
两张表并存迟早会出现「计划与实际打架、不知道以哪个为准」。
两个角色的分野靠两个事实判断：菜单日里有没有计划份数、当天有没有采集记录。
采集提交按实际整份覆盖菜单，但**把计划份数取回来留着**（`replace_items` 的
`planned.get(dish_id)`），于是「计划 812 份、实际做了 700 份」对得上。

采集页的候选清单因此**始终是整份菜品库**，菜单上的排在最前并标「计划」。
早先只在没有菜单时才列整库，结果是「菜单一旦排好，临时加一道菜就没地方勾」——
而临时换菜在后厨是常态。

大屏的口径由时序决定：菜单与单份营养在同步时就存在，所以早上就能显示；
油盐糖、食物种类那几项对照数据来自采集记录，采集之前如实显示「暂无数据」——
挂机大屏从早上开到晚上，不能拿「还不知道」冒充「已达标」。

**求解不出来的原因要能读到。** 求解器是纯函数、抛自己的 `InfeasibleError`，
但它携带的「卡在哪条约束」在 service 层被翻译成业务错误（422）——
早先它直接冒成 500，界面上只剩一句「服务器内部错误」，求解器白算。
实测还补了一条诊断：份数由预测给定之后，「少做点」这条退路没有了，
于是要能说出「按最少 4 道菜算，食盐合计已达 6.35 克，超过上限 5 克」这种话——
换菜换不动的时候，这是唯一能让看的人知道该改什么的说法。

### 批量排菜单：约束在「一段」里的接法

`POST /api/v1/menu-plan/batch/generate` 按日期区间逐日生成，
`POST /api/v1/menu-plan/batch/sync` 一键把这段区间导入当日数据（按区间而不是按一串 id：
刷新页面、换个人来点，结果都一样）。三处是批量独有的：

1. **上一天的菜要带进下一天的排除集**。「同一道菜不连续两日重复」原本靠查库里的菜单日，
   而这一批的菜单要等导入才落库——不带上，批量会排成连着两天同一道菜。
2. **均衡项**。只排除昨天那几道时，求解器每天都会从剩下的菜里挑出同一个最优解，
   一段菜单排成「A、B、A、B」两天一循环（实测 12 天只有 2 种组合）。所以加了一项
   「这一批里排得越多的菜越不该再排」的小penalty（`PlanWeights.variety`，默认 0.35）——
   它是偏好不是硬约束，压不过营养与预算。加上之后 12 天排出了 12 种组合。
3. **主食每天只排一份**（`CATEGORY_MAX[STAPLE] = 1`）。菜品库里只有两种主食，
   允许一天排两份，第二天就没有主食可排，直接「排不出来」——这是在批量里第一次撞见的，
   但它是通用问题（单日排菜单同样会把后一天堵死）。

单日生成仍然只排除「昨天」那几道：那正是需求里写的那条约束的对象。

### 知味膳食助手：受限工具 + 可换模型

助手是独立进程（`apps/agent`），分三层：工具白名单 `zhiwei_agent/tools.py`、
模型适配 `model.py`、会话编排 `runner.py`。它没有业务库凭据，只拿当前用户的
httpOnly Cookie 走业务 HTTP，所以「AI 不越权」落在进程边界上。

- **工具是任务级的，不是 REST 镜像。** 一个「查这道菜配方」工具同时返回每份食材、
  调味料与单份营养；模型少选一次就少错一次。权限、事务与口径仍由业务接口负责，助手不重算。
- **查询、体检、生成、解释**走工具；**发布与撤回**不经过模型，由页面按钮走独立路由调业务接口。
- **第一批只读工具（模块 33）**：看板指标、某天某餐供应与营养、菜品配方、食材营养、
  节假日与调休。原有工具另有菜品库、记录核查、数据体检、菜单方案、当前方案与逐项澄清。
- **单份营养取最强证据**：抽样实测 > 当日校准 > 标准配方理论值；结果带 `nutrition_basis`，
  回答必须把口径说清楚。
- **菜名有歧义就不猜**：按片段命中多道菜时只返回候选，让用户给完整菜名；工具不会自己选一道继续算。
- **看板不混日期**：今天尚未录采集时，最近一天的达标率可能为 0；工具把「区间总体」与
  「最后一个有数据的日期」分开返回，避免把今天读成「最近完整日」。
- **模型接入走 OpenAI 兼容协议**，`AGENT_MODE=auto|model|rules`；未配模型时退回规则模式并在界面标注，
  不假装连上。云端调用会把菜品级数据发给模型服务方，部署说明里写明。
- **身份不额外提权**：录入员能看的助手才能看；学校管理方只读。
- **不许编数据**：提示词要求先调工具，缺项照实说；数字要带日期、餐次、口径与来源。
- **对话与方案落 Agent 自己的 SQLite**（容器卷 `agent-state`），不写业务库；发布快照与撤回回执
  留在业务接口那边，便于审计。

## 四、前端结构

```
src/
├── app/          路由表、Provider、全局装配
├── features/<域>/  每个业务域内聚 api hooks、组件、页面、路由片段
├── layouts/      AdminLayout（电脑端）、DisplayLayout（大屏自适应）
└── shared/       UI 组件、hooks、工具、常量（膳食指南基准等）
```

`features/` 里有两个特殊成员：

- `intro/` —— 启动进场动画。它在 `main.tsx` 里包住整个路由，用 `inert` 遮住业务区；
  **公开大屏与 `/intro-preview` 不进动画**，系统设置里开了「减弱动态效果」的用户也直接进业务——
  表达性的动效不该挡住一个明确说了不要动效的人，也不该挡住自动化测试。
- `agent/` —— 知味膳食助手工作台，三栏：任务条件 / 对话 / 结果。它只调 `/agent-api/`；
  业务侧旧的 `features/assistant/` 抽屉已下线，系统只有这一个 AI 入口。

状态分层：

- **服务端状态**一律走 TanStack Query，不在业务代码里手写 loading/error 状态机。
- **客户端状态**目前几乎没有：当前用户与联网状态分别由 TanStack Query 的服务端缓存和一个
  普通 hook 持有，还没到需要引入状态库的地步（zustand 已在依赖里，留给后续真正跨组件共享的状态）。

采集页与抽样页的日期、餐次同步到地址栏（`?date=&meal=`）：录入员可以把「去录今天这餐」
的链接直接发给同事，刷新也不会跳回今天；端到端用例也能径直打开某一天，不必驱动日期控件。

「谁在写」的差别统一走 `features/auth/lib/permissions` 一处判断，不各写一份：
学校管理方在采集页看到只读视图，在抽样页看不到「录入实测」按钮。

### 侧边栏按使用动线分组

导航结构写在 `shared/config/navigation.ts`，**不按模块名归类**，按「人什么时候用它」排：

- **首页是数据看板**：打开系统第一个问题是「今天怎么样」，而不是「我要去哪个模块」；
  看到缺口再点进对应模块处理。看板内部再分「经营指标」与「今明菜单」两个页签：
  前者看趋势与达标，后者看今天、明天三餐已经采纳的菜单；未采纳的推荐草案不进入这里。
- **知味膳食助手**（`/admin/agent`）单列一项，不塞进「日常运行」：它是另一个工作台，
  不是某一页的附属功能。顶部还保留「AI 助手」抽屉——两者分工见第一节的对照表。
- **基础数据**（食材 / 调味料 / 菜品与配方）：一次性建库，三者有先后依赖，建好之后很少动。
- **日常运行**（明日菜单与采购 / 每日采集 / 抽样纠偏）：按时间顺序排——
  事前定菜单与采购、当天采集、每周抽样。「菜单推荐」与「采购预测」曾经是两页，
  定完菜单还要再点一次才看得到采购量，而菜单本身又只在有份数时才算得准；
  合成一页之后，一次生成、一套份数、一张采购单。

路径刻意保持扁平（`/admin/ingredients` 这类）：分组只影响导航怎么呈现，不影响地址。
`/admin/dashboard`、`/admin/forecast`、`/admin/recommendation` 都保留为跳转，旧的收藏不失效。

菜单用 `key={pathname}` 在换页时重建，让 `defaultOpenKeys` 按当前页重算——
比在 effect 里同步 openKeys 干净，也避开了「用户点开另一组又跳走」这类边界。

### 离线队列（唯一的客户端状态）

采集页断网时提交不了，但录入不能因此白填，所以有一条**本地队列**：提交失败先入队、
持久化在 localStorage，联网后自动补交。它落在采集域的 store 里，是与服务端无关的
纯客户端状态——这也是全项目唯一需要状态库的地方。

三个不那么显然的地方：

1. **只把网络层失败当作离线**（状态码 0 或 5xx）。服务端明确拒绝（4xx）说明数据本身有问题，
   排队只会让这条记录每次同步都被拒，那种情况必须当场告诉录入员去改。
2. **同一 (日期, 餐次) 只保留一条**，覆盖时界面要说清覆盖了哪一条。食堂通常一人录当天，
   行为可预期比策略精巧更重要。
3. **要把 mutation 的 `networkMode` 设为 `always`**。TanStack Query 默认的 `online`
   会把离线期间的请求**暂停在内存里**、联网后自动重放——看似省事，但这件事完全不可见：
   看不到有几条没交、卡在哪一条，刷新页面还会静默丢掉。这个坑是靠端到端用例才发现的。

路由级懒加载，每个业务域导出自己的路由片段，由 `src/app/router.tsx` 汇总挂载。

## 五、接口约定

- 原生 REST：用 HTTP 状态码表意，不做 `{code, message, data}` 全包。
- 错误体统一为 `{code, message, details}`。
- 分页统一为 `{items, total, page, page_size}`。
- 业务日期用 `DATE`（不含时间），时间戳用 `timestamptz`，时区统一 `Asia/Shanghai`。
- 前端类型由 OpenAPI 生成，`packages/api-client/src/schema.d.ts` 是唯一真源。

**有一处例外：Agent 的接口不遵守上面这套约定，也不共用同一个生成产物。**

- 路径前缀是 `/agent-api/v1/`，由 nginx 单独反代到 agent 进程；
- 对话接口返回 **NDJSON 流**（`start` / `trace` / `delta` / `done` 逐行推），
  因为它要边算边把「正在查菜品库」这类进度显示出来，等一次完整响应就没意义了；
- 类型单独生成到 `web/src/features/agent/api/schema.d.ts`（`pnpm gen:agent`），
  与业务契约 `packages/api-client` 互不影响。

两条契约各自生成、各自校验漂移，不强行统一——它们服务于两个进程，混在一起只会让
两边的发布互相牵制。

## 六、口径分离（本系统最容易出错的地方）

营养值有两个互相独立的口径维度，**禁止混用**：

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| `caliber` | 单份 / 人均 | 一道菜一份的营养 vs 当日总营养 ÷ 就餐人次 |
| `value_type` | 理论 / 校准 / 抽样 | 配方推算值 vs 当日闭环校准值 vs 抽样实测值 |

单份营养服务大屏与菜品查询，人均摄入服务看板与政策对标。把两者混用会得出完全错误的结论。

还有三类**数量口径**必须跟着标题一起读：

- 看板「供餐人次」是当天早餐、午餐、晚餐人数之和；选时间范围时显示这些日合计的平均值。
- 看板「平均每餐人次」不再作为标题，避免把三餐合计误读成单餐人数。
- 公开大屏支持早餐、午餐、晚餐切换：菜品来自哪一餐，人次、油盐糖和食物种类就只取哪一餐；接口用 `meal_type` 指定，前端默认按时间选餐，无菜单时不借用同日其他餐次。单餐对照条只把它作为每日基准的参考，不把单餐标签写成全天达标。

三份数值**并存不覆盖**，于是每个读取方都必须回答「我要的是哪一份」。这个判断收在
`app/shared/nutrition_values.py` 一处，取舍顺序为 **抽样实测 > 当日校准 > 配方理论**——
依据是证据强度：称过的是事实，闭环系数是从当日总用量反推的，配方理论值是基准。
公开大屏与管理端看板都用这一处，避免两个界面对同一道菜给出不同的数字。

## 套餐口径

推荐系统按“每人一份标准套餐”评估营养：入选的每道菜各贡献一个标准份，套餐营养是这些
单份营养之和。预测份数只用于采购量与出餐计划，不再乘进套餐的人均营养；否则预测某道菜
多做 1.4 倍就会被误算成一个人吃了 1.4 份。单份营养、套餐供给、实际人均摄入是三个不同口径。

## 七、三层校准：到底缩放什么

三层不是三个平行算法，而是同一条链上逐步逼近现实的三个台阶。共同的前提只有一句：
**食材是按配方称重下锅的，食材那一块可信；不确定的是油盐糖——它们靠手感。**
因此校准**只缩放调味料的贡献**，食材部分原样保留。

这条决定有一个很锋利的守卫：米饭、馒头这类不含调味料的菜，校准值必须与理论值分毫不差。
若图省事改成「整菜乘系数」，米饭的能量会被凭空抬高——测试里专门有一条用例盯着这件事。

| 层 | 数据来源 | 算出什么 | 落库标记 |
| --- | --- | --- | --- |
| 第一层 理论值 | 标准配方 | 按配方推算的单份营养 | `value_type=THEORETICAL` |
| 第二层 当日闭环 | 最近 6 周的油盐糖实际用量 | 每种烹饪方式下油 / 盐 / 糖各自的系数 | `value_type=CALIBRATED`，系数 `source=DAILY_CLOSURE` |
| 第三层 抽样纠偏 | 每周抽样称重实测 | 由能量反推的调味料整体系数 | `value_type=SAMPLED`，系数 `source=SAMPLING` |

**第二层**：**系数是从历史解出来的，不是当天的比值**。一天只有一个总用量，当天却有若干种
烹饪方式同时在用同一种调料，「当日总量 ÷ 某一种方法的推算量」在数学上无解——真那么算，
只要当天有两种以上烹饪方式，系数就会被放大成两三倍。正确做法是把最近 6 周的每次采集堆成
方程组：`某天某类调料总用量 = Σ(该类菜的配方推算量 × 该类菜的偏置)`，用带岭项的非负最小二乘
解出各烹饪方式的偏置（`engine.fit_calibration_coefficients`，纯函数、不碰数据库）。
拟合窗口截止到目标日前一天，目标日只做校验；每次采集的配方推算量来自 `daily_log_items.recipe_snapshot`，
不会因为之后修改配方而重算过去。
非负约束保证不会算出负的用量；岭项罚向 1 而非 0，因为无偏置时系数本来就是 1。
样本不足或某类调料只有一种方法在用时**退化成整餐一个比值并如实标注**，不硬解。
按烹饪方式分组因此是估计的**结果**，而不是把当天总量按方法硬拆——分组有意义，是因为
炒和蒸的用油量本来就不是一回事。

当天总量随之从「乘数」降级为**校验项**：拿系数预测当天用量，偏差超过 10% 放进 `checks`
提示核对。这通常是漏记了一道菜或总量抄错，正是采集环节最该被发现的错误。

不逐日采集的类别（酱油、淀粉等）不缩放，系数取 1 并在快照里说明。

**总量数据分辨不出单道菜。** 同一种烹饪方式内部，各道菜的比例只以「和」的形式进入方程，
A 菜多放、B 菜少放只要总和不变就观测不到。单道菜的真值只能靠第三层抽样称重获得，
这也是三层缺一不可的原因。

**第三层**：系数 = (实测能量 − 食材能量) ÷ 配方调味料能量。
差额全部归给调味料，是这一层唯一的推理步骤；食材部分按配方称重，不参与推导。
系数落在 `[0.5, 2.0]` 之外时，系统判定「这不是调味料手感的问题，更像配方录错了」，
**只保留实测证据并标记「疑似配方有误」，不写入系数**——硬套一个错系数，等于把一个错配方
校准成一个看起来自洽的错值，比不校准更糟。

**三层怎么汇到一处。** 缩放分两段乘在调味料贡献上，量纲不同所以是相乘而不是取其一：

    调味料贡献 × 当日闭环系数（按烹饪方式，第二层）× 抽样修正比（按菜品，第三层）

第二层答的是「这类做法长期比配方多放了多少」，第三层答的是「这道菜自己长期偏多少」。
抽样修正比按「菜品级优先、烹饪方式级兜底」取最新的一条，且**只作用于它当天及之后的日子**——
抽样是既有事实，不能反过来改写它之前已经算过的结果。

三层的值**并存不覆盖**。`GET /api/v1/calibration/comparison` 一次返回理论、校准、抽样三个值，
界面上摆在一起看，而不是让人猜「现在这个数到底是校准前还是校准后」。
抽样实测的误差区间由实测与推算的实际偏差决定（下限 5%），因此会比理论基准的 15% 更窄——
系统给的是「承认了多少把握」，实测吻合就该收窄，不该继续挂着理论区间。

公开大屏与管理端看板读的都是「当前证据最强的那一份」，因此只要测过一次，屏上就会改口
说称出来的数，并标明这份数值来自哪一层。

## 八、可追溯与留痕

- `dish_nutritions.computation_trace` 保存配方快照、所用校准系数与公式版本，任何数值都能回溯到来源与计算过程。
- 食材营养数据逐条记录来源与版本。
- 配方与菜单的修改通过 `audit_logs` 记录操作人、时间与前后值。

### 营养数据的来源与版本

食材与调味料的五项营养值、可食部比例，**只在 `apps/api/app/db/nutrition_reference.json`
这一份快照里定义**，种子脚本只负责把它落到库上、自己不写任何数字。

快照是从「食物营养成分查询平台」（中国疾病预防控制中心营养与健康所）逐条取数后生成的，
条目名与条目 ID 记在 `source_version`，原始 kJ 值、换算方式与查询日期记在 `note`。
取数与校验的工具是 [apps/api/tools/nutrition_reference.py](../apps/api/tools/nutrition_reference.py)：

| 命令 | 作用 |
| --- | --- |
| `pnpm nutrition:list <关键词>` | 列平台候选条目，人工挑条目时用 |
| `pnpm nutrition:fetch` | 按映射表取数并重写快照 |
| `pnpm nutrition:verify` | 重新取数，与已提交的快照逐条比对 |

映射表 `apps/api/tools/nutrition_sources.json` 记的是**条目 ID 而不是名字**：
同名近义条目太多（大米 → 稻米(均值)/粳米/籼米/香大米），按 ID 取才不会选错；
平台上没有对应条目的（目前只有蚝油）在表里显式留空，保留演示值并标着待核对。

**运行期不联网。** 第三方站点不给 SLA、可能改版、可能限流，做成运行期依赖等于把系统的
可用性押在别人身上；快照随仓库提交，取数是一次性的、可复核的动作。

两个口径约定写死在工具里：平台只给能量（kJ），千卡按 `1 kcal = 4.184 kJ` 换算并保留原始 kJ；
平台留空表示未检测，复合食品落库为 `NULL`（真未知），单一成分物质（油/盐/糖）按 `zero_fill`
显式记 0——哪种按哪种处理逐条写在映射表里，脚本不猜。

## 九、部署形态

面向**学校内网自部署**：`infra/docker-compose.yml` 一条命令拉起四个服务——
`postgres`、`api`、`agent`、`web`。

- **只对外暴露一个端口**（`${WEB_PORT:-8080}`），其余都在容器网络内；
- `/api/` 反代到 api，`/agent-api/` 反代到 agent，前后端同源，httpOnly Cookie 才走得通；
- api 容器启动时自动跑 `alembic upgrade head`；agent 容器等 api 健康后再起；
- agent 的对话数据落在独立卷 `agent-state`，**备份要连它一起备**，否则助手的历史会丢；
- 两个进程各自一份镜像、各自一份依赖（`apps/api/Dockerfile`、`apps/agent/Dockerfile`），
  发布时互不牵连。

完整说明见 [deployment.md](./deployment.md)。
