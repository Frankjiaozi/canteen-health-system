# 本地开发数据修复

Git 拉取的是代码，不会同步别人的数据库。`demo:prepare` 只在空库初始化，不会自动覆盖已有台账。这个工具用于新代码已合并，但本机独立开发库还缺新菜品、早餐历史或仍使用旧营养参考值的情况。

## 运行方式

在项目根目录执行，先查看预演报告：

```powershell
pnpm data:repair
```

默认不提交数据库变化。源数据在临时 PostgreSQL schema 中生成并回滚；目标修改也在事务内预演后回滚。报告中的 `changes` 是预计变化，`skipped` 是保留的自定义数据，`candidates` 和 `lunch_under_three_samples` 是剩余数据缺口。

确认报告后执行：

```powershell
pnpm data:repair --apply
```

如需升级已有的旧初始化午餐历史，必须提供**那次初始化的实际执行日期**。例如本次排查确认旧数据于 2026-10-16 创建，且逐字段匹配旧版本：

```powershell
pnpm data:repair --legacy-seed-date 2026-10-16
pnpm data:repair --legacy-seed-date 2026-10-16 --apply
```

不要照抄日期用于其他环境。不传日期时保留已有餐次；日期或内容不匹配时也不会覆盖。旧版本固定为仓库提交 `c51e43b921dd7946e1e2274d75551ac46070300f`，不是任意用户输入代码。浅克隆若缺该提交，应先补全 Git 历史。

## 边界与保障

- 只允许本机、非 production 配置，目标库固定为 `canteen_agent_demo`。不操作默认业务库、测试库或远程库。
- 数据库迁移须已完成；缺迁移先执行 `pnpm demo:prepare`。不要对现有台账运行完整 `db:seed`。
- 只添加缺失的初始化原料、菜品、配方、标准和空缺餐次。已有菜品、配方、单价、账号、密码和图片保持原样。
- 旧营养值必须与旧初始化数值及来源匹配才更新。人工修改值会列入 `skipped`。已有数据不会仅凭同名被认领；同名不同 ID 时中止并回滚。
- 历史升级须核对主表、菜品明细和配方快照；实测、校准或反馈记录不会作为普通初始化历史替换。更换初始化菜单时同步移除旧菜单遗留的理论营养结果。
- 改动后重新计算受影响的初始化餐次理论营养，并核对其他已有记录未被意外改动。实际经营历史不会通过补造记录来消除样本不足提示。
- 写入前锁定相关表并完成 `pg_dump` 备份，任一步失败都不提交。工具可能短暂阻塞本地写入，建议停止录入后运行。
- 报告仍有缺口时需要人工核对。历史方案、预测快照不会被改写；参考数据改变后，应重新生成待执行方案。

## 备份与报告

默认保存在 `apps/api/data/repair-backups/`，该目录已被 Git 忽略。不要提交数据库备份或个人台账。

优先使用本机 `pg_dump`；没有时使用项目 PostgreSQL 容器 `canteen-postgres-dev`，并校验其端口映射。可通过 `--postgres-container` 指定容器、`--backup-dir` 指定备份目录。备份失败不会继续执行；密码不会写入命令参数和报告。

恢复时先停止本地服务，并把备份恢复到**一个新建的本机数据库**核对，不要直接覆盖正在使用的库。例如使用本机 PostgreSQL 工具：

```powershell
createdb -h 127.0.0.1 -U canteen canteen_repair_restore
pg_restore -h 127.0.0.1 -U canteen -d canteen_repair_restore --no-owner --no-acl "备份文件的绝对路径.dump"
```

确认恢复内容后再决定切换数据库。备份包含原有账号及业务数据，应按本地敏感开发文件保存。
